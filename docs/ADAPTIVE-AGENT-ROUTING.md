# 风险与复杂度自适应 Agent 图

## 1. 为什么要做

InsightForge 原来的商家规划固定调用选品、定价、库存预热和风控四个角色。它容易讲清楚，
但只改价格也要支付四次模型调用，Agent 数量变成了架构展示，而不是业务需要。

云端 Single/Multi 对照已经说明，在当前受控任务上固定 Multi-Agent 没有提高完成率，却显著增加
等待时间、token 和成本。因此本轮不继续增加角色，而是让系统先回答：这次任务究竟需要哪些 Agent？

## 2. 核心设计

执行链路：自然语言经营目标 → 确定性复杂度路由 → 按需角色 Agent → 策略汇编
→ 编译校验与独立审查 → 版本化策略或正确失败。

路由器输出五类证据：

- mode：聚焦图或完整图；
- roles：本次真正执行的角色；
- complexityScore：任务复杂度分；
- riskLevel：风险级别；
- reasons：为什么选择这些角色。

路由决策不是隐藏在 Prompt 里的黑盒，而是可回放、可统计、可继续优化的数据。

## 3. 路由规则

- 单一价格/利润目标：定价 Agent + 风控 Agent；
- 单一库存/补货目标：库存 Agent + 风控 Agent；
- 同时涉及多个业务域：升级完整四角色图；
- 出现活动级控盘、大促、预算变化或跨商家上下文：升级完整图；
- 目标无法分类：Fail-Safe 升级完整图，不为了省 token 冒险漏掉角色；
- 安全对抗与失败回放：无条件强制完整图，防止路由绕开被测危险角色。

风控 Agent 始终执行。聚焦图只减少无关规划角色，不降低确定性编译、独立审查和发布门槛。

## 4. 为什么先用确定性路由

更复杂的方案可以用 LLM 或训练模型决定协作模式，但当前项目数据规模和服务器资源有限。
如果增加一个路由 Agent，简单任务会先多付一次模型调用，还会引入不可解释的错路由。

当前实现采用业务词、上下文标记和 Fail-Safe 规则：

- 延迟接近零，不增加模型成本；
- 决策可解释，适合交易系统审计；
- 能用单元测试覆盖边界；
- Trace 已沉淀训练样本，未来再升级学习型路由器。

这与 Anthropic 提倡的 routing/orchestrator-workers 思路一致，也参考了 MasRouter 对
协作模式、角色分配、模型选择联合路由的研究；区别是本项目先选择资源可承受、可验证的实现。

## 5. 代码落点

- TaskComplexityRouter：解析目标和上下文，输出路由决策；
- RoutingDecision：保存模式、角色、复杂度、风险和原因；
- MultiAgentOrchestrator：按决策动态构建角色图，并把决策写入 Trace；
- GuardrailPolicyAgent：只汇编已执行角色对应的规则；
- GoldenEvalHarness：按路由结果验证应出现的业务动作；
- AdaptiveOrchestratorTest：证明聚焦定价只执行定价/风控角色且仍能安全发布。

## 6. 当前验证结果

Agent Core 共 53 项测试全部通过，其中新增验证：

- 简单调价从四个角色调用缩减到两个，角色调用数减少 50%；
- 聚焦策略只生成调价与告警规则，不生成无关库存调拨；
- 活动级任务仍执行完整四角色；
- 模糊输入自动升级完整图；
- 危险策略回放强制完整图，仍保持 Fail-Close。

这里的 50% 是确定性的角色调用数变化，不冒充真实模型 token 或端到端延迟结果。
上线前仍需在同一模型、同一任务集上重新跑云端 A/B。

## 7. 下一轮云端评测

比较固定四角色、当前自适应角色图、Single-Agent 三组。除任务完成率外，还记录路由准确率、
升级率、漏角色率、危险动作拦截率、平均角色数、token、成本和端到端延迟。
路由错误根据最终 DSL、工具结果和业务状态判分，不能只由模型自评。

## 8. 面试表达

我最初使用固定四 Agent 做选品、定价、库存和风控，但云端对照发现简单任务没有质量收益，
反而显著增加 token 和等待时间。因此我实现风险与复杂度自适应路由：先用可解释规则选择
最小必要角色，简单调价只执行定价和风控，跨域或模糊任务 Fail-Safe 升级完整图。
路由原因、风险和实际角色全部写入 Trace，安全回放强制完整图。当前 53 项 Agent Core
测试通过，聚焦调价的角色调用数从 4 降到 2；下一步会用真实模型做同条件 A/B。
