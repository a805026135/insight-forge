# InsightForge QPS 与容量设计（面试可追问版）

## 0. 2026-08-25 本机负载整形 A/B（当前推荐数据）

在同一个 API 镜像、4 vCPU/1.5GiB/1GiB 堆、200并发条件下，每个新进程先执行一轮不计分的10000请求热身并等待 Reservation pending 清零，再各执行3轮10000个不同用户的完整鉴权秒杀入口：

- 普通方案：Redis 分布式滑动窗口每单一次网络往返，且每个成功订单发送一条 `sales.tick`；accepted QPS 为1541.01 / 1876.90 / 1642.45，中位数 **1642.45**；
- 本机方案：有界 Caffeine 本地滑动窗口负责单实例防刷，订单正确性仍由 Redis Reservation 负责；`sales.tick` 按 SKU 每50ms语义合并。accepted QPS 为1859.21 / 1967.76 / 1931.38，中位数 **1931.38**；
- 中位 accepted QPS 提升 **17.59%**，P95 从155.26ms降到147.89ms（-4.75%）；
- 代表性10000单活动的 `sales.tick` 从10000条压缩到100条（100:1）。它只负责唤醒规则引擎读取最新Redis库存，可靠的 `order.created` 和 Reservation 仍严格逐单保留；
- 两组共60000笔有效订单全部落库，每个活动库存10000→0，重复订单0、pending=0、无超卖。

第一次测试曾因切换配置时继承旧 Reservation backlog，出现9165接受、835次503；恢复队列上限正确阻止了无限接单，但该轮不属于独立容量样本，已排除。随后还发现100请求预热不足以消除JIT偏差，因此废弃早期34%的表面提升，改为两组都用10000请求热身，最终只保留17.59%的对等结果。原始结构化证据见 `docs/evaluation/local-seckill-workload-shaping-2026-08-25.json`。

这项优化不是把分布式限流“降级成不安全的本地变量”：单实例部署不需要跨实例共享防刷额度，本地有界窗口避免每单Redis RTT；真正的一人一单、库存原子扣减和恢复凭证仍在Redis Lua中。若扩为多个API实例，应切回 `distributed`，或把限流命令融合进Reservation Lua，不能继续把单机数字外推。

## 0.1 2026-08-24 本地 Docker 三轮 A/B 实测（历史组合优化）

在 Ryzen 5 9600X（6 核 12 线程、15.11GiB）主机的 Docker Desktop 中，Docker 可用内存约 7.318GiB；API 容器固定限制为 **4 vCPU、1.5GiB 内存、1GiB 堆**。MySQL、Redis、Kafka 与 API 同机，计时期间暂停无关 Dify 容器。commit `a81ded7`，每组 3 轮、每轮 3000 个不同登录用户、3000 库存、200 并发；登录与 1 个 Producer 元数据预热请求不计时。

- 普通方案（Kafka 同步 ACK + 每次查询活动 DB）三轮 accepted QPS 为 945.37 / 1027.99 / 1422.09，中位数 **1027.99**；
- 组合优化（可恢复异步 Reservation + 2 秒 Caffeine 活动缓存）为 1074.69 / 1573.20 / 1489.61，中位数 **1489.61**；
- 中位 accepted QPS 提升 **44.91%**，平均延迟中位数下降 **15.51%**，P50 下降 **16.26%**，P99 下降 **9.04%**；但 P95 从 223.93ms 上升到 238.80ms（**+6.64%**），不能表述为“所有尾延迟都下降”；
- 两组共 18,000 个请求全部接纳并最终落库，库存均归零，重复业务键为 0，Reservation pending 为 0，无超卖。

原始证据见 `docs/evaluation/local-seckill-qps-2026-08-24.json`。每轮只持续约 2～3 秒，因此它证明的是**本地短突发同版本 A/B**，不是 3～5 分钟稳态压测、云端容量或生产 SLO。面试与简历应写“三轮中位数约 1490 QPS、相对普通方案提升约 45%”，不能只挑 1573.20 QPS 的最好单轮，更不能改写成“大服务器实测”。

### 两个比正结果更重要的发现

第一，活动缓存开启后，只把同步 ACK 改为异步 Reservation，三轮中位数反而从 1455.67 降到 1321.78 QPS（约 **-9.20%**）。本机 Kafka ACK 很便宜，异步更快放量会增加消费者写 MySQL 的瞬时争用；这说明组合提升的主要贡献来自减少热点活动表回源，不能把全部收益归因于“上了 Kafka 异步”。

第二，最初未预热 topic/Producer 元数据时，`max.block.ms=50ms` 导致第一轮记录 110 次 Kafka 发送错误。HTTP 已接纳的 3000 个 Reservation 最终全部由正常消费或补偿器收敛为 3000 笔数据库订单，库存归零、pending 清零。它是 Reservation-first 可靠性的真实故障证据，但不是稳态容量证据；正式跑分必须先创建 topic 并执行少量不计时预热。

> 面试回答：本地 4 vCPU API 容器做了三轮 3000 用户、200 并发的完整入口 A/B。普通方案中位数 1027.99 accepted QPS，异步 Reservation 加 2 秒活动缓存后是 1489.61，提升约 44.9%，18,000 单全部对账且无超卖。不过单独异步化反而下降 9.2%，说明同机 Kafka ACK 不是瓶颈，真正收益主要来自减少活动表热点读取。P95 还上升了 6.6%，所以我只把它当短突发优化证据，不包装成生产 SLO。

## 0.2 2026-08-24 云端同版本 A/B 实测

阿里云 2 核、3.4GiB 单机，commit `b2962a5`，100 并发、每组 1000 个不同登录用户与 1000 库存。计时范围是完整秒杀 HTTP 入口，不含登录，并绕过公网 Nginx 限流：

- 普通方案：Kafka 同步 ACK + 每次查询活动 DB，**39.39 accepted QPS**，P95 **4751.86ms**；
- 优化方案：可恢复异步 Reservation + 活动元数据 2s Caffeine 缓存，**45.78 accepted QPS**，P95 **4109.34ms**；
- QPS 提升 **16.22%**，平均延迟下降 **15.11%**，P95 下降 **13.52%**；
- 两组均 1000/1000 接受、0 业务拒绝、0 基础设施错误，最终各落库 1000 单，DB/Redis 库存均为 0，无超卖。

原始结构化证据见 `docs/evaluation/cloud-seckill-qps-2026-08-24.json`。这是一轮受控证据，不是长期容量上限；简历宜写“云端同版本 A/B 提升约 16%”，不能写成生产 SLO。

### 为什么最后加入活动缓存

第一次只切换同步/异步时，异步组 37.86 QPS 低于同步组 40.78 QPS。负结果说明本机 Kafka ACK 不是主瓶颈，真正争用来自请求逐单查询活动表与消费者写库。最终增加最大 1000 条、写后 2 秒过期的 Caffeine 活动元数据缓存：同热点 key 回源由 loader 合并，最坏状态陈旧窗口明确为 2 秒；库存仍由 Redis Lua 原子管理，不拿本地缓存换超卖风险。开关 `INSIGHTFORGE_SECKILL_ACTIVITY_CACHE_ENABLED` 支持同镜像 A/B 和回滚。

压测还发现并修复两个生产问题：Kafka producer 超时参数的不变量现由测试保护；`sales.tick` 只是调价规则辅助链路，其同步元数据异常不能污染已接受的订单，可靠性仍由 `order.created + Reservation` 负责。

> 面试回答：我没有先调大线程池，而是做云端同版本 A/B。第一次异步化反而变慢；继续定位到活动表读和消费者写在争用 MySQL，才增加有界陈旧缓存。最终 accepted QPS 从 39.39 提升到 45.78，约 16.2%，P95 下降约 13.5%，两组库存都对平。单轮数字只作为优化证据，不包装成生产上限。

## 1. 先给结论，不虚报数字

当前有证据的数字是：隔离的 Redis Lua 热路径在本地 300 请求、100 工作线程、100 库存下为 **3114.82 RPS，P95 35.33ms**，且恰好 100 次成功、无超卖。它不含 HTTP、JWT、活动校验、Kafka 和 MySQL，**不能回答整站 QPS**。

此前云端商品查询容量结果错误率为 16.67%～43.33%，不能作为可用 QPS。现在可引用两组完整入口证据：阿里云 2 核单轮 A/B 为 39.39→45.78 QPS（+16.22%）；本地 4 vCPU 容器三轮短突发中位数为 1027.99→1489.61 QPS（+44.91%）。两者环境、并发和持续时间不同，不能横向推导“扩容倍数”，也不能把本地短突发写成云端生产容量。

面试时可以直接说：

> 我把容量拆成秒杀入口 accepted QPS 与数据库最终落单 TPS。Redis Lua 组件曾测到 3114.82 RPS，但我不会把它说成整站 QPS。完整 HTTP 链路在本地 4 vCPU 容器的三轮短突发中位数是 1027.99→1489.61 QPS，18,000 单最终全部对账；阿里云 2 核的受控单轮 A/B 是 39.39→45.78 QPS。两组数字都保留环境和限制，不外推生产 SLO。

## 2. 为什么不能只说一个 QPS

- **Offered QPS**：压测器每秒发出的请求数。
- **Admission QPS**：API 每秒完成校验并返回的请求数，包括成功、重复、售罄和限流。
- **Accepted QPS**：每秒真正创建新 Reservation 的订单数，不能把重复请求或售罄快速失败算成“下单成功”。
- **Settlement TPS**：消费者每秒最终写入 MySQL 的新订单数。
- **Recovery TPS / drain time**：Kafka 故障后补偿器每秒收敛多少预留、多久清空 backlog。

入口可以依靠 Redis 与 Kafka 削峰而短时大于数据库 TPS，差值会形成 Kafka backlog。系统是否健康不取决于入口数字最大，而取决于队列是否能在承诺时间内排空、错误率是否达标、库存与订单是否最终对平。

Little's Law 给出近似关系 `并发在途数 L = QPS λ × 平均延迟 W`。同步等待 20ms ACK 时，一个串行发送槽理论上最多约 50 次/秒；并发线程虽可掩盖等待，但会占用更多请求线程和内存。非阻塞投递将请求线程的等待从 broker 往返缩短为本地序列化与 producer 入队。

## 3. Phase 21 做了什么

### 3.1 可靠性前移：Reservation-first

Redis Lua 在扣库存时原子完成四件事：幂等判断、库存预扣、完整订单恢复载荷、pending ZSET 超时索引。它成为“请求已经被接受”的可恢复证据。Kafka 即使异步 ACK 失败，定时补偿也能按 ZSET 有界扫描并幂等落单。

因此生产者不再执行 `send().get(2s)`：

1. 请求线程把消息放入 Kafka producer 本地缓冲后立即返回；
2. ACK 失败由异步回调记录；
3. 补偿器依据 Reservation 重放，不依赖日志人工救单；
4. 同步序列化或本地入队异常仍立即走数据库短事务兜底。

这不是普通 fire-and-forget。普通异步发送在“Redis 已扣、Kafka 丢失”窗口可能永久丢单；本项目因为先持久化可恢复业务载荷，才具备安全异步的前提。

### 3.2 producer 批处理

`linger.ms=5`、`batch.size=64KiB`、LZ4 压缩让多个小订单事件合并成更少的网络请求。`acks=all` 与幂等 producer 保留，没有用牺牲可靠性换数字。5ms 是吞吐与尾延迟的折中，正式环境应通过 A/B 决定，而不是越大越好。

### 3.3 消费端并行

`order.created` 已有 3 个分区，旧配置却只有 1 个监听线程，另外两个分区不能并行落单。现在默认消费者并发为 3，并可通过 `INSIGHTFORGE_ORDER_CONSUMER_CONCURRENCY` 配置。

消费者并发不是越大越好：同一消费组可用并行度上限是分区数；继续加线程只会空闲。即使增加分区，也会受 MySQL 连接池、索引维护、redo log 和行锁约束。扩容应以 Kafka lag 下降且 DB P95、锁等待仍健康为准。

## 4. 云端 A/B 测试方法

使用 `deploy/benchmarks/seckill_capacity.py`。每个请求必须使用不同用户 JWT，因为服务端以登录身份覆盖 body 中的 userId；复用一个 token 测到的是幂等重复命中，不是新订单吞吐。token 文件不得提交 Git。

基线版本保留同步 ACK，优化版本使用异步 Reservation；两组必须满足：同一台云服务器、同一压测机、同 JVM 参数、同库存与用户数据、相同预热、相同并发阶梯。每轮先预热，再至少稳定运行 3～5 分钟，重复 3 次取中位数。

示例：

```bash
python3 deploy/benchmarks/seckill_capacity.py \
  --base-url http://127.0.0.1:8080 \
  --tokens-file /tmp/insightforge-jwts.txt \
  --activity-id 1 --sku-id 1 --concurrency 100 \
  --requests 5000 --variant async-reservation \
  --output /tmp/seckill-async-c100.json
```

压测前必须将库存设置到不小于请求数并预热 Redis，否则大部分请求会快速售罄，得到的是“拒绝 QPS”。正式记录以下数据：

- offered / admission / accepted QPS，业务拒绝数与基础设施错误数；
- P50、P95、P99，错误率；
- API CPU、GC、Tomcat 活跃线程与队列；
- Redis command latency、CPU、连接数；
- Kafka producer batch-size、request-latency、consumer lag；
- MySQL 新订单 TPS、连接池使用率、慢查询、锁等待；
- 压测结束后订单数、Redis 库存、DB 库存、重复订单数和 pending backlog。

发布门建议：基础设施错误率小于 0.1%，P95 达到业务目标，无超卖、无重复业务副作用，停止流量后 backlog 能在约定时间内归零。若这些条件没同时满足，峰值 QPS 再高也不算“可承载”。

## 5. 面试追问

**为什么不直接把 Tomcat 线程调大？** 线程只能掩盖阻塞，不能消除 Kafka RTT、DB 写入和锁竞争；过大会增加上下文切换和堆内存。先去掉同步等待、削峰并找到实际饱和资源，再按 CPU 核数和下游容量调整。

**异步返回后用户马上查订单，查不到怎么办？** 返回的是已接受的 Reservation 订单号，订单状态查询应能表达“处理中”；消费者或补偿完成后变为已创建。不能把暂时不可见误报为失败并让用户重复支付。

**Kafka 挂了为什么还敢返回成功？** 因为成功语义是“库存已原子预留且恢复载荷已持久化”，不是“数据库订单已写完”。Kafka 负责低延迟搬运，ZSET 补偿负责最终收敛。若 Redis Reservation 都没有成功，则不能返回接受成功。

**怎么继续扩展？** 单热点先做 Redis Cluster hash-tag 与热点分片评估；入口多实例无状态扩容；Kafka 增加分区并同步增加消费者实例；数据库按业务键分库分表或批量落单。每一步都要重新验证顺序、幂等、补偿和对账，不能只看吞吐。
