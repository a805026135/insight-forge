# InsightForge 面试题与回答

这份材料面向 Agent 应用工程师，也兼顾 Java 后端。不要逐字背诵；先掌握回答结构，再用你亲自运行和修改过的证据替换示例。

## 一、回答原则

一个可信回答通常包含四段：

1. 场景与约束：为什么这是问题。
2. 设计与链路：系统怎么做。
3. 取舍与失败：为什么不用其他方案，失败如何兜底。
4. 证据与边界：测试/指标/代码在哪里，还有什么没做。

避免只罗列技术名词，也不要把“写了配置”说成“经过百万并发生产验证”。

## 二、30 秒和 2 分钟项目介绍

### 30 秒版

“InsightForge 是一个智能电商和秒杀运营平台。我把 LLM 放在离线控制面，用 RAG、多 Agent 和 Critic 生成受限策略；高风险动作经过 HITL，再由 Drools 和交易服务确定性执行，模型不进入秒杀热路径。交易侧用 Redis Lua、Kafka 和数据库唯一/条件更新保证幂等防超卖；客服侧实现了查真实订单、退款草稿、用户确认、售后状态机和申诉闭环。同时建设了 40 条 RAG 评测、Prompt/知识版本、失败回放和 token/成本观测。”

### 2 分钟版

“项目有买家、商家两端。买家可以浏览、下单、支付、物流、评价和售后；商家管理商品、活动、订单、客服和 Agent。差异点有三条。

第一是 Agent 调价闭环。模型基于经营数据和商家知识生成受限 DSL，Critic 校验成本和权限，高风险动作需要人工确认，发布后由 Drools Worker 消费销售事件确定性执行。这样保留模型的分析能力，但不让概率性输出进入交易热路径。

第二是退款客服闭环。RAG 只解释政策，订单号、金额和状态来自数据库；Agent 生成草稿，用户确认后才调用售后事务接口，重复申请和越权由业务校验与状态机拦截。

第三是秒杀幂等。请求使用确定性业务键，Redis SETNX 和 Lua 做快速去重/预扣，Kafka 削峰，数据库唯一约束和 `stock >= qty` 条件更新最终兜底，并有取消补偿与对账。

工程上我还做了 40 条评测集。当前云端 Milvus 基线 Recall@4 97.14%、答案正确率 88.57%、拒答准确率 100%、P95 约 617ms；并记录 Prompt/KB 版本、trace、token、成本和失败回放。它目前是演示规模，不把这些数字包装成大规模生产结果。”

## 三、架构与工程问题

### Q1：为什么要做控制面/数据面分离？

答：秒杀要求低延迟、确定性和强一致库存，而 LLM 有网络延迟、概率输出、幻觉和成本波动。项目让 LLM 在离线控制面生成策略 DSL；在线数据面只读取已校验、版本化的策略，由 Drools 和普通 Java 服务执行。模型故障时继续用旧策略，不影响交易。

追问：如果策略错了？结构校验和业务护栏 Fail-Close，高风险动作 HITL；发布带版本，可回滚旧策略，执行留审计。

证据：`DslCompiler`、`ControlInstructionExecutor`、`AgentController`。

### Q2：为什么不是一个 Spring Boot 单体就够了？

答：业务代码仍采用 Maven 模块化单体以降低演示环境复杂度，但部署把 API 和 rule-engine-worker 分进程，避免规则计算挤占交易资源。模块边界还使 agent-core、seckill-core 可独立测试。若流量增长，可沿 Kafka 事件边界拆服务，而不是一开始承担分布式事务和运维成本。

追问：单体缺点？隔离和独立伸缩有限；数据库仍共享。当前规模下这是有意识的取舍。

### Q3：一次前端请求如何到数据库？

答：开发环境浏览器访问 Vite 5173，Vite 把 `/api` 代理到 8090；Controller 做协议和鉴权，Service 承担业务状态与事务，Mapper 访问 H2/MySQL，DTO 返回前端。生产由 Nginx 托管静态资源并反代 API。

证据：`vite.config.ts`、Controller/Service/Mapper、`deploy/nginx/nginx.conf`。

### Q4：local 与 integration/profile 有什么差别？

答：local 使用 H2 内存库并排除 Redis/Kafka/Redisson自动配置，目的是零依赖学习和测试；integration/生产连接 MySQL、Redis、Kafka 和 Milvus。local 成功不能证明中间件链路成功，所以发布前必须用 Compose 做集成验收。

### Q5：数据库为什么用 Flyway？

答：表结构必须可版本化、可重复部署、可审计。新环境从 V1 顺序迁移，生产更新只执行未应用版本。已执行脚本不可修改，否则 checksum 失败；修复要新增迁移。项目 H2/MySQL 共用主迁移，减少测试和生产漂移。

### Q6：怎样保证密钥不泄漏？

答：仓库只提交 `.env.example`；`.env` 和交接文档被 gitignore，生产 Compose 对 JWT/Grafana 密码设必填。模型 key 通过环境变量注入，不写 YAML、镜像或日志。上线还需密钥轮换和云密钥服务；当前仓库未实现自动轮换，应诚实说明。

## 四、Agent 与 RAG 问题

### Q7：这里的 Agent 和普通聊天机器人有什么区别？

答：它不仅生成文本，还围绕目标做检索、规划、受控工具调用、状态管理和结果校验。调价最终形成版本化 DSL 并驱动规则执行；退款最终形成草稿，经确认调用事务 API。能否改变真实业务状态，是区分“聊天壳”和 Agent 应用的重要证据。

### Q8：多 Agent 是怎么划分的？为什么不一个大 Prompt？

答：Planner 拆任务，选品/定价/库存/风控角色处理不同上下文，Independent Critic 单独校验结果。拆分有利于权限、Prompt、评测和失败定位，但增加 token、延迟和编排复杂度。简单问题仍应走单 Agent/规则路径，不能为了“多 Agent”而多 Agent。

### Q9：ReAct 循环怎样防止无限调用？

答：运行时限制最大步骤、重试和预算；工具参数做 JSON Schema 校验；取消/暂停通过运行状态门控制；异常终止记录 trace。生产还应给每工具超时、熔断和幂等 key。

### Q10：工具调用如何保证安全？

答：先按角色暴露最小工具集合，参数做结构校验和资源归属校验，写操作生成草稿或进入 HITL，服务端再次鉴权与状态校验。Prompt 只是行为引导，不是权限边界。退款、调价等工具还必须幂等并记录审计。

### Q11：RAG 的完整链路是什么？

答：文档按来源和商家清洗，切块并保留 docKey/merchantId/version metadata，Embedding 后写向量库；查询先做意图路由和安全门槛，再带商家过滤检索 Top-K，把证据交给模型。答案保留来源，低相关或越权问题拒答/转人工。

证据：`KnowledgeBaseService`、知识表迁移、40 条 dataset。

### Q12：为什么既用 MySQL 又用 Milvus？

答：MySQL 保存文档主数据、版本和审计，是可恢复真相源；Milvus 保存向量索引用于相似度检索，可重建。订单、金额、权限等结构化事实直接查 MySQL，不应该向量检索。这样索引损坏不会丢失原始知识。

### Q13：如何做商家知识隔离？

答：写入时 metadata 带 merchantId，查询时根据 JWT 商家身份强制过滤，缓存 key 也带 merchantId，结果返回前可再校验来源。越权样本进入评测集。不能依赖用户传 merchantId，也不能只靠 Prompt。

### Q14：如何减少幻觉？

答：先把问题分成结构化事实、知识问答和事务动作；结构化事实查数据库，知识问答要求有证据，事务动作经工具和确认。检索前做路由，检索后设相关性/事实门槛，缺证据正确拒答；输出再做 schema/业务校验。幻觉不能“彻底消灭”，只能通过边界和评测降低风险。

### Q15：Prompt 版本管理具体保存什么？

答：保存 promptKey、不可变版本、完整内容、SHA-256、创建时间；trace 记录实际使用版本。上线新版本可对同一评测集对比，失败回放可复现上下文。仅在 Git 里改 Prompt 不足以回答线上某次请求用了什么版本。

### Q16：知识库版本怎么管理？

答：业务文档有稳定 docKey，正文变化创建不可变快照并关联版本；向量索引是该版本派生物。索引更新失败时不应把“已发布”指向半成品，恢复可由 MySQL 快照重建。

### Q17：什么是失败回放？

答：从历史 trace 选失败样本，用保存的输入、Prompt/知识/模型版本和工具上下文重新执行，比较旧/新结果。它用于回归定位，不应默认再次执行真实退款/调价写操作；回放工具需只读、沙箱或 dry-run。

### Q18：token 与成本统计有什么价值？

答：用于单请求诊断、模型/Prompt 对比、预算告警和容量规划。只看总 token 不够，还应按 Agent、模型、场景和成功/失败聚合，并同时看延迟和正确率；低成本但答错没有价值。价格会变化，单价配置应版本化而不是硬编码成永久真相。

## 五、评测问题

### Q19：40 条评测集怎么构建？

答：按真实能力分层采样：商品/活动/政策/运营知识的可回答问题，以及未知事实、秘密、跨商家和绕过审批的不可回答问题。每条保存期望 docKey、关键事实、是否应拒答和商家范围。失败样本继续加入集合，不能为了指标好看删除。

### Q20：Recall@4 怎么算？

答：只对可回答样本，若期望文档出现在前四条检索结果就记 1，命中数除以可回答样本数。它衡量检索有没有把证据送进上下文，不等于最终回答正确。

### Q21：答案正确率怎么判？

答：当前离线判分要求命中期望文档且返回上下文覆盖所有标注关键事实，优点是确定、便宜、可回归；缺点是不能完全评价自然语言质量。下一步可引入人工抽检或 LLM-as-Judge，但要校准 judge 偏差和版本漂移。

### Q22：拒答率与拒答准确率有什么区别？

答：拒答率是所有请求中拒答占比，越高不一定好；拒答准确率关注本该拒答的样本是否被正确拒答。还要看可回答问题被误拒的比例，否则系统可以靠“全拒答”拿到虚假的安全感。

### Q23：P95 为什么比平均延迟重要？

答：平均值会掩盖少量慢请求，P95 表示 95% 请求在该值内，更贴近尾延迟体验。当前约 617ms 是 40 条云端检索基线，不是高并发端到端 SLA；数据量小，应该结合更多轮次、P99和并发压测。

### Q24：当前 88.57% 正确率够上线吗？

答：不能脱离场景回答。低风险 FAQ 可结合引用和人工兜底灰度，高风险退款/调价不能由该正确率直接自动执行，必须靠结构化工具、状态机、护栏与 HITL。当前还有 4 条失败，适合作为作品集基线，不应宣称已达到所有生产要求。

### Q25：怎么证明优化不是过拟合评测集？

答：把数据分开发/回归/保留集，失败样本只进入下一版本回归集；按意图和商家切分，保留未见表达；上线灰度观察真实反馈。当前 40 条规模有限，应明确下一步扩到更多真实会话并做人工标注一致性。

## 六、高并发与一致性问题

### Q26：怎样防超卖？

答：Redis Lua 在热路径原子检查/预扣提升吞吐，数据库用单条 `UPDATE ... WHERE stock >= qty`，受影响行数为 1 才成功，保证最终库存不为负。异步链路还需订单唯一约束、失败补偿和对账。分布式锁是辅助协调，不是库存正确性的唯一来源。

### Q27：怎样保证同一用户只买一单？

答：业务键包含 activityId、activitySkuId、userId并生成确定性订单号；Redis SETNX 快速拦重复，数据库唯一约束最终兜底。前端查询购买状态后禁用按钮改善体验，但后端仍必须验证，因为请求可绕过前端。

### Q28：Redis 扣了库存，Kafka 发送失败怎么办？

答：这是跨资源一致性窗口。可靠方案是记录可恢复状态并重试/补偿，例如本地事务 outbox 或可靠消息，配合幂等消费者和对账。项目已有幂等、补偿/巡检思路，但回答时应按代码当前实现说明，不能把规划中的 outbox 说成已上线。

### Q29：Kafka 重复消费如何处理？

答：消费者按确定性 orderId 落库，DB UNIQUE 是最后防线；业务更新也要用状态条件或幂等记录。offset 提交只能减少重复，无法保证业务副作用永不重复，所以所有消费者都按 at-least-once 设计。

### Q30：取消订单如何回补库存？

答：先以状态条件把可取消订单转为取消，只有本次状态迁移成功者执行一次回补；普通与秒杀订单按来源回补对应库存视图。重复取消应返回幂等结果而不能再次加库存。还需对账处理“状态成功但回补失败”的异常窗口。

### Q31：为什么不直接用数据库悲观锁？

答：悲观锁正确但热点 SKU 会串行等待，连接和锁竞争限制吞吐。Redis Lua 把快速拒绝前置，Kafka 削峰，DB 条件更新兜底，减少数据库压力。低并发普通下单直接事务/条件更新反而更简单，因此按场景选择。

## 七、退款客服案例追问

### Q32：为什么 Agent 不直接提交退款？

答：退款是有财务影响的不可忽视写操作，模型可能理解错订单或原因。项目先展示真实订单、金额和草稿，由用户二次确认后调用事务 API；商家审核和申诉由状态机管理。Agent 拥有建议和参数准备权，不拥有无限执行权。

### Q33：用户重复点退款怎么办？

答：前端禁用只能改善体验；后端检查订单归属、当前状态和是否已有活跃售后单，事务/唯一业务规则保证只有一份有效申请。重复请求返回已有结果或明确冲突，不重复创建。

### Q34：如何避免 Agent 编造订单？

答：可退款订单来自 JWT 用户限定的数据库查询，模型只在返回集合中选择；工具层再次校验 orderId 归属。RAG 不参与生成订单事实，输出引用真实订单号与金额。无订单时正确失败或转人工。

### Q35：商家拒绝后怎么办？

答：售后状态从 APPLIED 进入 APPROVED/REJECTED；被拒可 APPEAL，进入复核，再决定退款或维持拒绝。买家和商家共享数据库中的同一工单状态，聊天文本不能单独改变结果。

## 八、测试、部署与可观测问题

### Q36：测试策略是什么？

答：单元测试覆盖 DSL、知识检索和服务状态；并发回归证明无超卖；API 测试覆盖鉴权和事务；前端使用 TypeScript 类型门与生产构建；Compose 做真实中间件集成；评测集做 Agent 回归。2026-08-12 本地全量测试为 141 tests、0 failures/errors、7 skipped，但应以面试前最新运行结果为准。

### Q37：线上 Agent 答错怎么排查？

答：先用 traceId 定位版本和时间，再按顺序检查输入/身份、意图路由、检索文档与分数、Prompt/模型版本、工具参数/结果、护栏和前端确认。区分检索失败、生成失败和事务失败，然后把样本加入回归集并做失败回放。

### Q38：如何部署和回滚？

答：前端先构建，Compose 构建 API/Worker 镜像，`.env` 注入密钥，Nginx 只暴露 80/443，数据组件留在容器网络。更新前记录 commit/镜像和备份 volume，部署后做 health 与业务冒烟；失败则恢复旧镜像/commit和兼容数据库。数据库迁移若不可逆，需要 expand-contract，而不是简单回滚 jar。

### Q39：2C4G 为什么容易出问题？

答：MySQL、Kafka、Milvus/etcd/MinIO、两个 JVM 和监控同时运行，内存峰值容易 OOM。Compose 已限制堆和容器资源，但演示可临时停监控，长期应升级 4C8G、拆服务或使用托管组件，并基于 `docker stats`/指标容量规划。

### Q40：项目目前最大的不足是什么？

答：评测集只有 40 条且判分偏确定性；缺更大规模并发和故障注入证据；部分跨 Redis/Kafka/DB 一致性可用 outbox/CDC 加强；HITL/回放还需更严格的审计与 dry-run；模型和 Embedding 成本基线需要长期真实流量。诚实说不足并给优先级，比声称“没有明显 bug”更专业。

## 九、反向追问面试官

可以选择两三个：

- 团队的 Agent 主要是知识问答、工作流执行还是开放式规划？高风险工具如何做权限和 HITL？
- 当前评测以离线集、线上反馈还是 LLM-as-Judge 为主？Prompt/模型版本如何关联到 trace？
- RAG 的文档规模、多租户隔离和 P95 目标是什么？是否使用 reranker/混合检索？
- Agent 平台如何处理失败回放，怎样避免回放再次产生真实副作用？
- 团队更看重模型效果、平台工程还是业务闭环，我入职前三个月最需要解决什么问题？

## 十、面试前自测清单

- 不看文档讲完 30 秒和 2 分钟版本。
- 现场画出总架构、退款时序和秒杀幂等时序。
- 能打开代码指出五个证据：`SeckillService`、条件扣减 Mapper、`KnowledgeBaseService`、`DslCompiler`、`RagEvaluationService`。
- 能解释四个评测指标的分母与局限。
- 能说出三个失败场景及兜底，而不只讲理想流程。
- 能诚实区分本地兜底、云端实测、规划项。
- 自己从新目录克隆并按搭建文档跑通一次。
