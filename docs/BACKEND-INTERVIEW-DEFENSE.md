# InsightForge 后端面试答辩手册

这份文档不是把 Java、MySQL、Redis、Kafka 的定义重新抄一遍，而是训练一种面试能力：先讲清原理，再指出项目中的真实落点，最后主动说明边界。建议与 [架构设计与技术选型](ARCHITECTURE-DESIGN-GUIDE.md)、[项目面试题与回答](INTERVIEW-QA.md) 配合阅读。

## 一、先建立回答模板

遇到任何后端问题，都按下面五步回答：

1. 定义：它解决什么问题。
2. 原理：关键机制是什么。
3. 选型：为什么适合当前约束，替代方案是什么。
4. 落地：项目中哪个链路、类、SQL 或测试使用了它。
5. 边界：它不能保证什么，故障时如何兜底。

例如“为什么用 Redis”不能只答“因为快”。更完整的回答是：秒杀库存是热点共享状态，直接压 MySQL 会产生锁和连接竞争；Redis 在内存中执行命令，Lua 可把检查库存与扣减组合为一次原子操作，因此适合前置快速拒绝。但 Redis 不是订单真相源，缓存成功不等于数据库落单成功，所以项目仍使用确定性订单号、数据库唯一约束、条件更新、补偿和对账。

## 二、项目介绍的三个长度

### 30 秒版本

InsightForge 是 Java 21 与 Spring Boot 3.3 实现的智能电商和秒杀平台。交易侧实现可恢复库存预留协议，用一段 Redis Lua 同时完成幂等、扣库存、恢复载荷与超时索引，Kafka 负责削峰，MySQL 短事务和 ZSET 补偿负责最终收敛；智能侧使用风险与复杂度自适应 Agent 图生成受限策略，再由规则引擎确定性执行。

### 2 分钟版本

项目包含买家购物、秒杀、支付、物流、评价、退款申诉，以及商家商品、活动、订单、客服和运营 Agent。核心设计是把概率性智能与确定性交易分开：LLM 负责分析和生成受限 DSL，高风险动作经 Critic 与人工确认，线上交易只执行已发布、可回滚的规则。

秒杀链路以 `(activityId, activitySkuId, userId)` 形成稳定业务身份。旧方案把 SETNX、扣库存和发消息分开，存在占位未扣减、扣减未发消息的故障窗口；现在由 Lua 原子创建包含完整订单载荷的 Reservation 并登记 ZSET 截止时间。Kafka 正常时异步落库，异常时同步收敛或由补偿器重放同一数据库事务；唯一键和条件更新保证重放无重复副作用。完整追问见 [可恢复库存预留协议](RECOVERABLE-SECKILL-PROTOCOL.md)。

评测不是只测 RAG。云服务器实测包含 40 条 RAG 集和 50 条 Agent 集。50 条 Single-Agent 为 30/30 正向成功、20/20 安全拦截，P95 6.887 秒，平均 475.22 token；同集 Multi-Agent 质量没有提升，但 P95 55.008 秒、平均 4237.02 token，因此当前证据支持“默认单 Agent，复杂任务再路由多 Agent”，而不是盲目多 Agent。

### 10 分钟展开顺序

1. 业务问题与角色。
2. 控制面和数据面分离。
3. Agent 调价、退款闭环、秒杀幂等三个案例。
4. Redis、Kafka、MySQL 的职责边界。
5. 评测、可观测和故障恢复证据。
6. 当前不足和下一步优先级。

不要从技术栈清单开始。面试官更关心“为什么这样设计”和“失败后会发生什么”。

## 三、Java 集合与并发基础

### HashMap 为什么不是线程安全的

Java 8 的 HashMap 主要由数组、链表和红黑树组成。key 经过扰动后定位桶；碰撞少时用链表，桶内元素达到阈值且数组容量足够时树化，降低极端碰撞下的查询复杂度。扩容会重新分布桶，平均查询接近 O(1)，但这不是严格保证。

它不保证并发读写的可见性和结构一致性。并发 put、resize 或“先判断再修改”的复合操作都有竞态。项目中的商家、订单、Agent 运行状态不能仅靠进程内 HashMap 保证多实例一致；真相状态放 MySQL，热点协调放 Redis，进程内集合只适合无共享要求的临时计算或测试桩。

追问“为什么不用 Hashtable”：Hashtable 对大量方法整体加锁，接口和扩展性较旧；通常按需求选择 ConcurrentHashMap、不可变 Map 或外部存储，而不是机械替换。

### ConcurrentHashMap 的关键点

Java 8 的 ConcurrentHashMap 不再使用旧版 Segment 作为主要结构。读路径大量依赖 volatile 可见性，更新通过 CAS 和桶级 synchronized 协作，减少全表锁竞争。它保证单个方法的线程安全，但 `if (!map.containsKey(k)) map.put(k, v)` 仍是非原子复合操作，应使用 `putIfAbsent`、`computeIfAbsent` 等原子 API。

项目映射：即使本地用 ConcurrentHashMap 记录“用户已购买”，多实例之间仍看不到彼此状态，因此秒杀幂等必须落到 Redis 原子命令和数据库唯一约束。

### volatile、synchronized、Lock 和 CAS

`volatile` 保证可见性，并通过内存屏障约束相关指令重排；它不能让 `count++` 变成原子操作。`synchronized` 同时提供互斥和可见性，JVM 能进行锁消除、锁粗化等优化。`ReentrantLock` 基于 AQS，适合需要可中断锁、超时获取、公平策略或多个 Condition 的场景，但必须在 finally 中释放。

CAS 是比较并交换，适合低冲突的原子状态更新；高冲突时会自旋消耗 CPU。ABA 问题是值从 A 变 B 又回 A，单纯比较值无法发现中间变化，可用版本戳解决。

项目映射：单 JVM 锁只能保护一个 API 实例。秒杀防超卖依赖 Redis Lua 和数据库条件更新；规则执行的 Redisson 锁用于跨实例协调，但锁本身不能替代库存约束与幂等。

### JMM 与 happens-before

Java 内存模型定义线程之间何时可见，而不是简单等同于 CPU 缓存。常见 happens-before 规则包括：解锁先于随后对同一锁加锁；volatile 写先于随后读；线程 start 前的操作对新线程可见；线程中的操作先于 join 成功返回。

面试时可联系 Agent 异步编排：共享可变状态若没有安全发布，即使单元测试偶尔通过，也可能读取旧值。优先使用不可变对象、消息传递、并发容器和明确的持久化状态。

### 线程池如何配置

ThreadPoolExecutor 的核心参数是核心线程数、最大线程数、队列、空闲时间、线程工厂和拒绝策略。典型执行顺序是先创建核心线程，再入队，队列满后扩到最大线程，仍无法接收才拒绝。无界队列可能让最大线程数失去意义，并把过载变成内存积压。

CPU 密集任务通常接近核数，I/O 密集可以更多，但最终上限受数据库连接池、Redis 连接、模型 API 配额和下游吞吐约束。不能背一个固定公式后直接上线。

项目映射：多 Agent 并行不能只追求更大线程池。云端 A/B 已显示多 Agent 平均 token 是单 Agent 的约 8.9 倍、P95 是约 8 倍；应先按任务复杂度路由，并设置并发、队列、超时、预算和拒绝策略。

### CompletableFuture 常见陷阱

默认异步方法可能进入 commonPool，容易与其他任务争抢；异常若未通过 `exceptionally`、`handle` 或 join/get 观察，会被悄悄遗漏；多个 future 组合时仍需超时和取消；阻塞 I/O 放入计算池会拖慢其他任务。

项目回答：为 Agent 角色并行使用专用受限执行器，透传 traceId，设置每角色与整条任务预算。失败要区分可重试超时、业务拒绝和非法输出，不能统一吞掉后返回空字符串。

## 四、Spring 与事务高频追问

### IoC 和 AOP 到底解决什么

IoC 把对象创建、依赖关系和生命周期交给容器，业务代码面向接口协作；AOP 通过代理统一处理事务、鉴权、日志和指标等横切逻辑。Spring Boot 的自动配置根据 classpath、配置和条件创建 Bean，它减少样板代码，但不等于不需要理解具体 Bean 从哪里来。

项目映射：API、Agent、持久化和规则模块通过依赖注入组合；local profile 排除 Redis/Kafka 自动配置，集成环境再装配真实中间件。profile 是启动期组合，不是运行时高可用机制。

### Bean 生命周期与循环依赖

常见生命周期包括实例化、属性注入、Aware 回调、BeanPostProcessor 前置、初始化、后置以及容器关闭时销毁。AOP 代理通常由后置处理器创建。

构造器循环依赖无法靠“三级缓存”自然解决；即便某些单例字段注入可以被提前暴露，也会增加半成品对象和代理一致性风险。设计上应拆职责、引入事件或重构依赖方向，而不是把允许循环依赖当功能。

### `@Transactional` 为什么会失效

常见原因包括：同类内部自调用绕过代理；方法不可被代理；对象不是 Spring Bean；异常被捕获后未重新抛出；默认只对 RuntimeException 和 Error 回滚；另起线程后事务上下文不自动传播；数据库表或连接不支持事务。

项目映射：普通同步下单把订单插入和数据库库存条件更新放入短事务。模型调用、Redis Lua 和 Kafka 发送是外部资源，不能指望数据库 `@Transactional` 一起回滚。跨资源一致性依赖状态记录、幂等、补偿和对账。

### 事务传播和隔离怎么回答

REQUIRED 加入现有事务或新建事务；REQUIRES_NEW 挂起外层并创建新事务，会额外占连接；NESTED 通常依赖保存点。传播行为是在回答“方法调用时如何加入事务”，隔离级别是在回答“并发事务互相能看见什么”，两者不要混淆。

长事务会长期占用连接、锁和 undo，远程模型调用不应放在事务中。先完成可失败的外部分析，再在短事务中校验最新业务状态并提交，避免基于过期草稿直接写入。

### Spring MVC 请求链路

请求通常经过 Nginx、Servlet Filter、DispatcherServlet、HandlerInterceptor、Controller、Service、Mapper，再由消息转换器序列化响应。Filter 更接近容器层，适合通用认证或 trace；Interceptor 能感知 Handler；AOP 适合方法级横切。异常应由统一异常处理转换为稳定错误码，不能把堆栈直接返回前端。

项目映射：JWT 只证明身份声明经过签名校验，资源归属仍必须在 Service/查询条件中校验。前端隐藏商家按钮不是鉴权。

## 五、MySQL 与数据库设计

### InnoDB 为什么常用 B+Tree

B+Tree 节点扇出高，树高低，适合磁盘页和范围扫描；数据集中在叶子节点，叶子有序相连。InnoDB 主键索引叶子保存整行，是聚簇索引；二级索引叶子保存主键值，查询非覆盖列可能需要回表。

索引设计遵循最左前缀。联合索引顺序要结合等值条件、范围条件、排序和选择性；覆盖索引可以减少回表，但索引过多会增加写放大和存储。索引失效不是一条死规则，应以实际 SQL、统计信息和 EXPLAIN 为准。

项目映射：订单常按 userId 或 merchantId 加状态、时间查询；幂等依赖业务唯一索引而不是普通索引。面试前要能现场指出订单唯一键、活动 SKU 查询和售后状态查询对应的迁移脚本。

### MVCC、undo log 和 Read View

MVCC 让一致性读通过版本链读取合适快照，减少读写互斥。旧版本通常依赖 undo log，Read View 根据活跃事务范围判断版本是否可见。READ COMMITTED 一般每次一致性读创建新视图，REPEATABLE READ 通常在事务内复用视图，因此两次查询结果可能不同。

快照读不等于所有操作无锁。当前读、UPDATE、DELETE、`SELECT ... FOR UPDATE` 仍会加锁。长事务会阻碍旧版本清理并放大 undo 压力。

### 行锁、间隙锁和死锁

InnoDB 的锁依附索引记录；没有合适索引可能扫描并锁住更多记录。REPEATABLE READ 下为防止特定范围幻读，当前读可能涉及 next-key lock。死锁无法靠统一锁顺序完全消灭，但可以缩短事务、按固定顺序访问资源、建立合适索引，并捕获死锁后做有界重试。

项目映射：热点库存使用单条条件更新，而不是先 select 再 update：

```sql
UPDATE activity_sku
SET stock = stock - :qty, sold = sold + :qty
WHERE id = :id AND stock >= :qty;
```

受影响行数为 1 才表示成功。并发事务在数据库内部串行修改同一记录，条件会基于更新时状态重新判断，从而避免库存变成负数。

### 唯一约束为什么是幂等最后防线

Redis SETNX 可能过期、丢失或只在一个降级分支生效；服务重试和 Kafka 重投也会绕过前端。稳定 orderId 配合数据库 UNIQUE，使重复副作用最终落不进去。消费者收到重复事件时，应把唯一冲突识别为“已经处理”的幂等结果，而不是系统未知错误。

不要说“数据库保证消息 exactly-once”。更准确的表述是：消息仍可能至少一次投递，但确定性业务键和数据库约束让建单这个业务副作用呈现 effectively-once。

### 慢 SQL 如何排查

先确认是否真的慢以及影响范围，再看慢查询日志、EXPLAIN/EXPLAIN ANALYZE、扫描行数、索引选择、回表、排序/临时表、锁等待和连接池。优化顺序通常是修 SQL 和索引、减少返回数据、缩短事务，再考虑缓存或分库分表。

不要一看到慢就加 Redis。低命中、高一致性、写多读少的数据可能不适合缓存；错误索引和 N+1 查询也不会因缓存自动消失。

## 六、Redis 高频追问与项目回答

### Redis 为什么快

主要原因是内存访问、紧凑数据结构、单线程执行命令避免大量共享数据锁竞争，以及 I/O 多路复用处理大量连接。Redis 6 之后可用 I/O 线程处理部分网络读写，但命令执行原子性的核心理解仍是主线程顺序执行。

“单线程所以快”并不完整。大 key、长 Lua、复杂集合命令会阻塞其他请求；持久化、复制和网络也会形成尾延迟。

### 数据结构如何选

- String：计数、库存、幂等标记、序列化对象。
- Hash：对象字段或同一实体的紧凑属性。
- List：简单队列，但可靠消息通常应使用 Stream/Kafka 等方案。
- Set：无序去重和集合运算。
- ZSet：排行榜、按时间或分值排序。
- Bitmap/HyperLogLog：布尔状态和近似基数统计。
- Stream：带消费组的 Redis 消息流。

项目中库存、幂等键、限流和实时价是 Redis 合理落点；订单、售后状态和财务事实仍在 MySQL。

### Lua 为什么能保证原子，局限是什么

脚本在 Redis 服务器内作为一个命令顺序执行，中间状态不会被其他命令插入，适合把“判断库存、判断重复、扣减”组合起来。它减少网络往返，但不提供跨 Redis 与 MySQL/Kafka 的事务原子性。脚本运行过长还会阻塞实例，因此应短小、参数化并有回归测试。

### 缓存穿透、击穿和雪崩

穿透是大量查询不存在的数据，可用参数校验、空值短缓存或布隆过滤器；击穿是热点 key 失效瞬间并发回源，可用互斥重建、逻辑过期或提前刷新；雪崩是大量 key 同时失效或 Redis 故障，可用 TTL 抖动、多级缓存、限流降级和高可用。

项目中的 SKU 缓存是带 TTL 的快照，不是实时库存真相。秒杀扣减使用专用库存 key，不能把普通商品缓存中的 stock 当原子库存。

### RDB、AOF、高可用和淘汰

RDB 是时间点快照，恢复快但可能丢失最近窗口；AOF 记录写命令，数据更完整但体积和重写成本更高。主从复制提高读扩展和故障恢复能力，但异步复制仍可能丢最近写入。Sentinel 解决监控和主从切换，Cluster 解决分片与容量扩展。

TTL 删除通常结合惰性删除与定期抽样；达到 maxmemory 后按配置执行淘汰策略。幂等键被淘汰会削弱快速去重，因此必须保留数据库唯一约束，并监控 evicted_keys、内存和热 key。

### 分布式锁要注意什么

正确的锁至少要有唯一 owner、原子加锁和过期、只允许 owner 解锁。业务执行超过租期会出现锁提前释放，Redisson 看门狗可续期，但进程长暂停、网络分区仍需考虑。对于要求严格顺序的外部副作用，可加入 fencing token，让存储拒绝旧持有者。

项目回答：Redisson 锁用于规则执行的跨实例协调；秒杀库存正确性不依赖“抢到锁”，而依赖 Lua、条件更新和唯一键。

## 七、Kafka 与事件驱动

### Topic、Partition、Consumer Group

Topic 是逻辑消息类别，Partition 是并行和顺序的基本单位。同一消费组内一个分区同一时刻只分配给一个消费者，因此有效并行度受分区数限制。同一 key 路由到同一分区可获得分区内顺序，但 Kafka 不提供跨分区全局顺序。

项目映射：订单事件应以稳定业务键分区，使同一订单相关事件尽量有序；增加消费者数量超过分区数不会继续提高并行度。

### ack、幂等生产者和投递语义

`acks=all` 配合合理副本配置提高已确认消息的持久性；幂等生产者减少重试导致的分区内重复。它们不能保证数据库副作用只执行一次，也不能自动解决“数据库提交成功但 offset 未提交”的窗口。

消费者通常按 at-least-once 设计：先处理业务，再提交 offset；崩溃可能导致重复，所以落库必须幂等。先提交 offset 再处理则可能丢业务消息。

### Rebalance、积压和背压

消费者加入退出、订阅变化或超时会触发 Rebalance，暂停消费并重新分配分区。单次处理过慢可能超过 poll 约束而被移出组。排查积压要看生产速率、消费速率、lag、处理耗时、分区倾斜、下游 DB 和失败重试。

盲目增加消费者可能把压力转移到 MySQL。应同时限制批大小、消费者并发和数据库连接，必要时暂停或降级入口。

### 重试、死信和毒消息

瞬时网络错误适合指数退避的有界重试；参数非法、状态不允许等永久错误不应无限重试。超过阈值的消息进入死信或失败表，保留原消息、异常、次数、版本和 traceId，再由人工或修复任务处理。

项目中的补偿与对账用于发现 Redis、Kafka、DB 之间的异常窗口。当前不能宣称所有跨资源窗口都由事务 Outbox 完整覆盖；若继续生产化，优先加入 Outbox/CDC、失败表和可操作告警。

### 为什么是 Kafka，不是 RabbitMQ

Kafka 适合高吞吐、可回放事件流和消费者各自维护 offset；RabbitMQ 的路由、单条消息确认和传统任务队列体验更直接。项目需要销售事件供订单、规则和评测等消费者独立处理，并希望可回放，所以选 Kafka。若只是低吞吐退款任务、复杂路由和即时确认，RabbitMQ 同样合理。

## 八、分布式一致性与高并发秒杀

### CAP、BASE 和本项目取舍

网络分区发生时，分布式系统无法同时无条件保证一致性和可用性。CAP 不是平时“任意三选二”的产品标签，而是分区条件下的取舍。BASE 强调基本可用、软状态和最终一致，是一些异步业务的工程策略，不代表所有字段都可以不一致。

项目中订单唯一性和库存不为负是正确性底线；Redis 库存视图、Kafka 落单和数据库状态允许短暂不同，但必须能补偿和对账。支付金额、订单归属不能靠最终一致随意放松。

### 一次秒杀请求的答辩链路

1. 后端校验身份、活动时间和 SKU，不信任前端状态。
2. 稳定业务维度生成确定性 orderId。
3. Redis 幂等闸门与 Lua 原子预扣，快速返回重复、售罄或成功。
4. 发送 Kafka 订单事件，把数据库落单移出峰值请求线程。
5. 消费者按 orderId 幂等写订单，并执行库存最终落库逻辑。
6. 数据库 UNIQUE 和 `stock >= qty` 条件是最后防线。
7. 发送失败、消费失败、超时未落单由补偿任务和对账发现并修复。

### 典型故障矩阵

- Redis 扣减失败：不发建单事件，返回明确失败。
- Redis 扣减成功、Kafka 发送失败：释放幂等/回补预扣或记录待补偿状态；不能只记录日志。
- Kafka 重复投递：数据库唯一键和状态条件返回幂等结果。
- DB 落单失败：重试可恢复错误，永久失败进入失败表并回补/人工处理。
- 接口超时但后端成功：客户端用相同业务键查询结果，不能生成新随机订单号重试。
- Redis 数据丢失：由数据库重建活动库存视图；唯一约束仍阻止重复订单。

### Outbox、Saga、TCC 如何选择

Outbox 把业务数据与待发送事件写进同一数据库事务，再由轮询或 CDC 投递，适合解决 DB 提交与消息发送窗口。Saga 将长事务拆成局部事务和补偿，适合可补偿业务流程。TCC 显式设计 Try/Confirm/Cancel，控制强但侵入和资源预留成本高。2PC 提供更强原子协调，但可用性、锁持有和性能成本不适合秒杀热路径。

项目当前采用本地事务、幂等、补偿和对账，Outbox 是明确的增强方向，不能在面试中说成已经上线。

## 九、JVM、网络和线上排障

### JVM 运行时区域和 GC

重点关注堆、线程栈、元空间、直接内存和 Code Cache。对象主要在堆，类元数据在元空间；线程多会消耗栈和本地内存，所以容器只配置 `-Xmx` 仍可能 OOM。

Java 21 通用服务常用 G1，在吞吐、停顿和内存间平衡；ZGC 面向更低停顿，但换收集器不能修复对象泄漏或无限队列。排障应看 GC 日志、分配率、停顿、晋升、堆转储和容器 memory.events，而不是先复制网上参数。

### CPU 100%、OOM 和接口变慢怎么查

CPU 高：先定位进程和热线程，再用 jstack/jcmd 或 profiler 对照线程栈；区分业务计算、锁自旋、GC 和序列化。内存高：区分 Java heap、direct memory、线程、page cache 和其他容器，必要时生成 heap dump 看支配树和增长路径。接口慢：从入口 P95/P99 下钻 trace，再检查线程池队列、连接池、慢 SQL、Redis 延迟、Kafka lag、模型调用和 GC。

不要在生产直接频繁生成大 heap dump 或开启高开销 profiler。先评估磁盘和停顿，优先低开销观测。

### TCP、HTTP 和连接池

TCP 三次握手建立双方收发能力和初始序列号；四次挥手是因为全双工两个方向分别关闭。TIME_WAIT 让迟到报文过期并保证最后 ACK 可重传。大量短连接会增加握手、端口和 TIME_WAIT 压力，应合理使用 keep-alive 和连接池，但连接池过大又会压垮下游。

HTTP 504 表示网关等待上游超时，不等于模型一定失败。本项目 50 条同步云端评测曾触发 Nginx 504，而内部任务仍需更长时间，这说明批量评测更适合“提交异步任务 → 查询进度/结果”，不应单纯无限增大代理超时。

### JWT、XSS、CSRF 与接口安全

JWT 的签名保证未被篡改，不加密 payload；需要校验签名、过期、issuer/audience 等必要声明。无状态 token 撤销较难，可用短 access token、refresh token、token version 或黑名单。浏览器把 token 放在哪里会影响 XSS/CSRF 风险，不能用一句“JWT 防 CSRF”概括。

项目必须在服务端校验 userId/merchantId 归属；RAG 的租户过滤从认证上下文派生，不能相信请求体传入的 merchantId。Prompt injection 也不能只靠系统提示词，要靠最小工具权限、结构化参数、业务校验和 HITL。

## 十、Agent/RAG 工程追问

### 为什么不用 GraphRAG

GraphRAG 适合实体关系丰富、多跳推理频繁、需要沿图解释关系的知识。当前商家知识以商品、政策和运营说明为主，云端数据规模不大，多数查询是单跳事实检索；引入图抽取、实体消歧、图存储和双索引一致性会增加资源和评测成本。当前优先使用 metadata 过滤、向量/词法检索和事实门槛。

这不是“服务器小所以永远不用”。当失败样本持续表现为跨文档关系推理问题，并且普通混合检索和 rerank 无法解决时，再用保留集证明 GraphRAG 的质量收益是否覆盖复杂度。

### 为什么 Multi-Agent 没有默认启用

云端同一 50 条集上，Single 与 Multi 都得到 30/30 正向成功和 20/20 安全拦截；Single P95 6.887 秒、平均 475.22 token，Multi P95 55.008 秒、平均 4237.02 token。当前受控任务上 Multi 没有提准，却显著增加延迟和成本，因此默认使用单 Agent/确定性工作流，只把跨领域规划等复杂任务路由给 Multi-Agent。

面试边界：20 条对抗样本是同一“低于成本价非法 DSL”的多种表达，不等于覆盖 20 类安全风险；50 条也不是生产分布或隐藏集。

### 如何解释 100% 指标

40 条 RAG 云端连续三轮在当前数据集上 Recall、事实判定和拒答判定均为 100%；50 条 Agent 集也全部通过。正确表述是“当前版本在这组受控回归集上的结果”，不是“系统准确率永久 100%”。还需独立隐藏集、更多风险类别、人工一致性、线上真实分布和版本漂移监控。

### token、成本和延迟为什么一起看

任务成功率是结果，unsafe rate 是安全，P95 是用户体验，token/成本是资源效率。只降 token 可能损害正确率，只提高成功率可能用不可接受的成本换来。应比较单位成功成本，并按模型、Prompt、Agent 角色、场景和版本聚合。

Langfuse/内部 trace 用来记录单次调用上下文、模型、token、成本和 span；Prometheus 适合聚合 QPS、错误率和延迟。traceId 不能直接作为 Prometheus label，否则会产生高基数时间序列。

## 十一、面试官压力追问示范

### “用了 Redis 和 Kafka 就叫高并发吗？”

不能。组件只能说明架构意图，高并发结论必须包含压测模型、数据量、并发、持续时间、P95/P99、错误率、资源饱和、库存对账和恢复结果。当前项目有防超卖、Lua、容量及故障恢复测试，但 2C4G 演示环境不应包装成百万 QPS 生产案例。

### “Kafka 不是 exactly-once 吗，为什么还要唯一键？”

Kafka 的幂等和事务能力有明确边界，不能自动覆盖任意数据库副作用。消费者可能在 DB 提交后、offset 提交前崩溃，消息会重投。业务唯一键和状态条件是最终副作用幂等的必要防线。

### “数据库条件更新已经防超卖，Redis 是否多余？”

在低并发下可以只用数据库，这也是 local 同步路径的意义。热点秒杀时 Redis 的价值是把售罄和重复请求在数据库前快速拒绝，减少连接、锁和日志压力；数据库仍负责最终正确。是否保留 Redis 应由压测和复杂度收益决定。

### “为什么评测接口会 504？”

50 次真实模型调用超过同步 HTTP 网关等待窗口。把代理超时调大只能缓解，不能解决资源占用、断线和进度不可见。工程方案应将批量评测改成异步 Job，持久化进度，客户端轮询或订阅状态，并支持取消、恢复和结果下载。

### “完整 Maven 测试现在是绿的吗？”

最近修复了 50 条扩容后硬编码断言和知识刷新异步等待的确定性问题；随后云端全量运行超过 66 分钟，受资源竞争/超时影响未拿到可审计的完整绿灯结果。已完成的单项云端评测证据可引用，但不能把这次全量运行说成通过。下一步应拆分测试层、为外部模型测试单设 profile 和超时，并在资源窗口重新跑全套。

### “项目最大的技术债是什么？”

第一，跨 Redis、Kafka、MySQL 的异常窗口还可用 Outbox/CDC 和失败表加强；第二，Agent/RAG 数据集仍是受控小样本，安全类别不够多；第三，批量评测需要异步 Job；第四，单机 Compose 缺多节点容灾和长期 SLO 证据。优先级应先保证交易一致性和可恢复性，再扩评测代表性，最后扩基础设施规模。

## 十二、简历写法与不可夸大边界

可以写：

- 设计控制面/数据面分离的 Agent 电商平台，以版本化 DSL、Critic 与 HITL 隔离 LLM 和交易热路径。
- 使用 Redis Lua、Kafka、确定性业务键及 MySQL 唯一/条件更新构建秒杀幂等链路，并通过并发、防超卖和故障恢复测试验证。
- 建设 50 条 Agent 与 40 条 RAG 云端评测，比较 Single/Multi-Agent 的任务成功、安全、P95、token 和成本，基于证据选择默认单 Agent 路由。
- 实现 Prompt/知识版本、trace/span、失败回放和 Langfuse token/成本观测。

不能写：

- “生产百万 QPS”——没有对应规模的实测证据。
- “严格 exactly-once”——当前是至少一次消息加业务幂等。
- “Agent 准确率永久 100%”——只是当前受控回归集结果。
- “完整测试已全部通过”——最近一次云端全量套件没有取得完整成功报告。
- “使用 GraphRAG”或“Outbox 已上线”——它们是分析过的备选/增强方向。

## 十三、七天面试训练法

第 1 天：不看文档讲 30 秒和 2 分钟项目介绍，录音并删掉技术名词堆砌。

第 2 天：手画总架构、秒杀时序和退款状态机，能解释每条箭头失败怎么办。

第 3 天：复习 Java 集合、JMM、锁、线程池，并把每题映射到多实例和 Agent 编排。

第 4 天：复习 Spring 代理、事务失效、MySQL 索引/MVCC/锁，现场解释条件扣减 SQL。

第 5 天：复习 Redis、Kafka、一致性和补偿，完成一次故障矩阵口述。

第 6 天：复习 RAG、Agent、安全与评测，解释 Single/Multi 对比为什么改变架构选择。

第 7 天：按本文件压力追问做 45 分钟模拟面试；每个回答必须包含证据和边界。

最终标准不是“背完八股”，而是面试官从 Redis 追到 MySQL、从 Kafka 追到幂等、从 Agent 追到评测时，你仍能围绕同一套业务约束给出一致答案。
