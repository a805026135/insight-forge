# 选做 8：RAG 知识库设计（场景 · 知识资产 · 注入策略）

> 对应代码：`insightforge-agent-core/.../kb/`（Phase 19）
> 一句话定位：**LLM 的记忆外部化** —— 把“平台规则、商家商品、历史决策”这类低频静态知识放进向量库，
> 问答时检索增强，让回答有依据、可溯源、可商家隔离，而不是靠模型瞎编。

---

## 1. 为什么这个项目需要 RAG

商家 AI 助手这类场景，大模型的通病是：

| 问题 | 表现 | RAG 的解法 |
|---|---|---|
| 幻觉 | 回答编造商品库存/平台规则 | 只基于检索到的知识库片段回答，片段即“依据” |
| 时效性 | 模型训练数据里没有本店商品 | 商品/决策从 MySQL 实时生成入向量库 |
| 隔离性 | 模型不知道“你是谁” | 每块知识带 `merchantId`，检索按商家过滤 |
| 可解释 | 答完说不出处 | 回答强制标注《来源》，知识库可查可审计 |

边界：**RAG 管“低频静态知识”，实时结构化数据（订单、库存快照、销量）走 SQL/统计**，
不要把所有数据都塞进向量库——数字会过期，向量检索给不出精确数字。

---

## 2. 使用场景矩阵（哪里需要 RAG）

| 场景 | 使用者 | 现状 | 注入的知识 | 隔离粒度 | 落地优先级 |
|---|---|---|---|---|---|
| 商家 AI 运营助手 | 商家 | ✅ 已上线 | 平台手册/FAQ + 本店商品目录 + 本店历史决策 | 商家级（平台知识全校可见） | P0（已做） |
| 动作批准前规则校验 | 商家 | 🟡 部分 | 运营手册（上下架/调价/秒杀规则） | 商家级 | P1：让 agent 在生成动作建议前先检索规则，降低违规动作 |
| 买家智能客服 | 买家 | ⬜ 规划 | 商品卖点、售后政策、FAQ、订单/物流查询 | 用户级（订单数据仅本人） | P1 |
| Agent 离线规划/复盘 | 平台运营 | ⬜ 规划 | 历史活动方案、相似活动效果（替换 `MemoryStore` 关键词桩） | 平台级 | P1 |
| 运营大屏可解释 | 平台运营 | ⬜ 规划 | 指标口径说明、结论依据 | 平台级 | P2 |
| 风控/合规红线 | 全端 | ⬜ 规划 | 禁售清单、敏感词、合规条款（强制注入，不进可检索池） | 平台级 | P2 |

原则：
- **平台级知识**（merchantId=0）：所有商家可见，如运营手册、FAQ、活动规则。
- **商家级知识**（merchantId=N）：仅该商家可见，如商品目录、历史决策。
- **用户级知识**：仅本人可见，如买家订单、收货地址——订单类数据建议走结构化查询而非 RAG。

## 3. 知识资产清单（注入什么内容）

### 3.1 已接入

| 知识类型 | docKey 规范 | 来源 | 归属 | 更新时机 | 用途 |
|---|---|---|---|---|---|
| 平台运营手册 | `platform/playbook` | 静态资源 `kb/playbook.txt`（秒杀/上下架/定价/库存/发货/售后/AI 使用规范） | 平台级 | 代码发布时 | 规则问答、动作建议依据 |
| 平台 FAQ | `platform/faq` | 静态资源 `kb/faq.txt` | 平台级 | 代码发布时 | 常见问题问答 |
| 买家售后政策 | `platform/buyer-policy` | 静态资源 `kb/buyer-policy.txt`（退货/退款/物流/发票/客服） | 平台级 | 代码发布时 | 售后政策问答、买家客服知识源 |
| 商家商品目录 | `merchant/{id}/products` | `product` 表按商家聚合（名称/分类/售价/库存/状态/描述） | 商家级 | 启动时缺省入库 + `/api/merchant/kb/reindex` 手动刷新 | 商品咨询、卖点、库存说明 |
| 商家历史决策 | `merchant/{id}/decisions` | `audit_log` 中该商家已批准执行的动作 | 商家级 | 同上 | 复盘、相似场景建议 |
| 商家活动与促销规则 | `merchant/{id}/activities` | `activity` + `activity_sku` 表聚合（活动名/时间/秒杀价/库存/已售） | 商家级 | 同上 | 活动问答、秒杀参与建议 |

### 3.2 规划中（按价值排序）

| 知识类型 | docKey 规范 | 来源 | 归属 | 更新时机 | 用途 |
|---|---|---|---|---|---|
| 售后/客诉经验 | `merchant/{id}/aftersales` | 售后工单、退款原因聚合 | 商家级 | 定时 | 售后问答、改进建议 |
| 历史活动方案复盘 | `platform/history-plans` | `agent_trace` + 评估报告 | 平台级 | 活动结束后 | Agent 规划时参考相似方案 |
| 竞品/市场资料 | `platform/market` | 外部数据导入 | 平台级 | 手动 | 定价与选品建议 |

### 3.3 明确“不进 RAG”的数据

- 订单、库存、销量等**实时指标**：走 SQL/Redis，保证精确与时效。
- 用户隐私（手机号、地址）：只走结构化查询 + 权限校验，永不入向量库。
- 需要强一致性的规则（价格下限、风控红线）：走 Drools/规则引擎，RAG 只做解释与提示。

## 4. 检索与注入策略

### 4.1 数据链路

```
知识源（静态资源 / MySQL 表）
  → TextChunker 切块（400 字符/块，50 字符重叠，中文按句号/段落切）
  → EmbeddingProvider（生产 DashScope qwen3.7-text-embedding 1024 维；
                        无 key 本地词法向量兜底）
  → VectorStore（生产 Milvus HNSW+COSINE；本地/测试 SimpleVectorStore）
  → metadata：docKey / title / sourceType / merchantId（0=平台）
```

### 4.2 检索

- 入参：`merchantId + 问题文本`。
- 取回：`topK=4` 展示，候选先取 `topK*8`（24）再过滤，避免召回不足。
- 隔离：候选按 `metadata.merchantId ∈ {0, 商家}` 在 **Java 侧强制过滤**（两种向量库行为一致，绝不越权）；
  生产数据量上来后可下推 Milvus 过滤表达式（Spring AI `SearchRequest.filterExpression`，已支持，属优化项）。
- 无命中兜底：明确回答“知识库未收录该内容”，禁止编造。

### 4.3 Prompt 注入格式（商家助手现状）

在经营数据上下文之后追加：

```text
【知识库参考】（检索自商家知识库，可能相关）
- 《平台运营手册》秒杀活动规则：……
- 《商家商品目录》华为 MatePad Pro 13.2：库存 530，售价 5199……
请优先参考以上知识库资料回答，并简要说明依据来源。
```

要求：回答引用《来源标题》，来源缺失时不得断言具体数字。

### 4.4 动作批准前的规则校验（P1 改进点）

现状：`ask()` 识别到动作后，先按动作类型检索运营手册（PLAYBOOK）片段，
把“价格不得低于成本”“参与活动的商品不建议下架”等约束拼进建议卡片描述，作为**批准前置检查**。

## 7. RAG 与 Memory 的边界（重要）

不要把“记忆”和“知识库”混为一谈，二者职责不同：

| 维度 | RAG（知识库） | ShortTermMemory（短期记忆） | LongTermMemory（长期记忆，规划中） |
|---|---|---|---|
| 存什么 | 事实/规则/商品/活动（可引用、需隔离） | 当前会话的问答上下文 | Agent 运行经验/历史方案/复盘结论 |
| 来源 | 静态资源 + MySQL 业务表 | 对话过程 | agent_trace / 评估报告 / 决策 |
| 生命周期 | 跨会话长期有效，随业务数据更新 | 会话内，cap 40 条（当前 20 条） | 跨会话长期，按相似度召回 |
| 检索方式 | 向量检索 + 商家隔离 | 顺序窗口直接拼接 | 向量检索（未来可复用 VectorStore） |
| 归属 | 平台级 / 商家级 / 用户级 | 商家级（每商家一份） | 平台级 |
| 失败兜底 | 明确“知识库未收录”，禁止编造 | 直接丢弃最旧 | 无命中则不参考 |

本项目落地对照：
- **进 RAG**：平台运营手册、FAQ、买家售后政策、商家商品目录、商家历史决策、商家活动规则。
- **进 Memory（短期）**：商家助手多轮对话的历史问答（`MerchantAssistantService.conversations`，
  每商家一个 `ShortTermMemory`，cap 20 条），让“那华为呢”这类指代问题能接上上文。
- **进 Memory（长期，下一步）**：Agent 离线规划的历史活动方案与复盘——届时用向量库存“经验”
  而不是“事实”，与 RAG 知识库同引擎不同源。
- **都不进**：订单/库存/销量实时指标（SQL）、用户隐私（结构化查询 + 权限）、强一致规则（Drools）。

## 6. 面试要点（30 秒版）

1. **为什么 RAG**：商家场景知识更新快、强隔离、要可溯源，RAG 把模型记忆外部化。
2. **为什么 Milvus**：生产选 Milvus（HNSW+COSINE）；2C4G 约束下本地/测试用 SimpleVectorStore，
   Spring AI `VectorStore` 抽象保证切换只改配置——这是工程取舍不是偷懒。
3. **为什么切块**：400 字符 + 50 重叠，中文按句切，兼顾召回与上下文完整。
4. **为什么隔离放 Java 侧**：向量库过滤表达式在不同实现下行为不一致，Java 侧过滤对两种存储都严格成立，
   量大了再下推 Milvus。
5. **哪些不进 RAG**：实时指标走 SQL、隐私走结构化查询、强一致规则走 Drools——RAG 不是万能存储。
