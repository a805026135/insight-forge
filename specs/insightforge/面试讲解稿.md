# InsightForge 面试讲解稿（Q&A）

> 用途：把 Phase 0–11 的项目，变成面试时「问不倒」的讲解。每个问题给**回答要点 + 大白话类比 + 可被追问的细节**。
> 风格：先说人话，再上技术；诚实标注边界（面试官最恨「吹上线」）。

---

## A. 项目定位与整体（必问开场）

**Q1：你这个项目是干什么的？为什么做它？**
- 要点：智能秒杀 / 大促平台，核心矛盾是「高并发强一致（防超卖）」+「AI 智能决策（选品/定价/库存）」如何共存。
- 大白话：秒杀像「厕所就 100 个坑位，1 万人同时冲」，必须保证不超卖；AI 像「聪明的店长，离线算好今天哪些货该降价、哪些该从别的仓调货」。店长不能冲在门口收门票（太慢会堵死），所以让他**提前写好规则**，门口检票机按规则自动执行。
- 可追问：为什么不用 LLM 直接回应用户？→ 见 C 节「控制面/数据面分离」。

**Q2：这项目是 demo 还是真能上线？**
- 要点：后端全链路 `mvn` 实跑通过（96 测试全绿）；但前端 / Docker / JMeter / CI 在本沙箱写就未实跑，已显式标注，不虚报。
- 注意：诚实说「未实跑」比吹「已部署」安全得多——面试官一追问就露馅。

---

## B. 高并发 / 防超卖（最常深挖）

**Q3：秒杀怎么防超卖？**
- 要点（分层）：① DB 原子条件更新 `UPDATE activity_sku SET stock=stock-? , sold=sold+? WHERE id=? AND stock>=?`，受影响行数=1 才成功，这是唯一真相；② Redis+Lua 原子预扣减削峰；③ Redisson 分布式锁守护跨实例互斥；④ Kafka 异步建单 + 幂等去重；⑤ 状态机 + 对账兜底（初始库存 - 成功单 = 剩余）。
- 大白话：先抢「数据库里的真库存」，Lua 是门口快速发号，锁是防止两个服务员同时改同一张表，对账是打烊点货对账。

**Q4：为什么不用乐观锁（`@Version`）？**
- 要点：乐观锁仍需额外 `stock>=?` 条件才能真正防超卖（单靠版本号重试不保证不扣成负的）；条件更新已内置原子性，且用受影响行数直接判成功，更简单可靠。`version` 字段保留给对账。
- 可追问：条件更新在高并发下会不会大量失败重试？→ 配合 Redis+Lua 预扣 + 令牌桶限流，把流量削到 DB 能稳接的程度，失败重试可控。

**Q5：Redis+Lua 预扣减和 DB 扣减怎么保证一致？**
- 要点：Lua 做「快速失败」的第一道闸门（库存不足直接回），DB 条件更新做「最终真相」；对账服务核对 Redis/DB 与「初始-已售」。承认：本项目 Redis 与 DB 一致性走对账兜底，未引入 Seata 强一致事务（范围红线，延后 M7+）。

**Q6：限流怎么做？缓存怎么设计？**
- 限流：Redis+Lua 滑动窗口，按（用户, 活动）维度，member 用 INCR 序号防同毫秒撞车；本地无 Redis 时退化内存版，超限返 429。Nginx 令牌桶 / Sentinel 留作部署纵深（诚实标注未实跑）。
- 缓存：Caffeine(L1)+Redis(L2) 多级；防击穿=`get(key,loader)` 单飞；防雪崩=TTL 随机抖动；防穿透=NULL 哨兵。
- **关键纪律**：缓存只读、限流只在入口，**热路径的扣减/建单/幂等原封未动**——缓存限流是「加在旁边」，不是「改核心」。

## C. AI Agent 架构（项目灵魂）

**Q7：你这个 Agent 和传统「调个 LLM 接口」有什么不同？**
- 要点：自研运行时（工具注册 + JsonSchema 校验 / ReAct 循环 / 三层记忆 / Critic 反思重试），不止是 prompt。模型接 Spring AI + DeepSeek（条件启用），默认离线确定性桩。
- 大白话：不是「问一句答一句」，而是有「工具箱 + 短期记忆 + 长期记忆 + 干错了对自己复盘重试」的小团队。

**Q8：为什么 LLM 不进秒杀热路径？这是怎么保证的？**
- 要点：**控制面 / 数据面分离**。LLM 只在离线侧生成护栏 DSL（策略），由 Drools 在线确定性执行。热路径（扣减/调价/再分配/下单）零 LLM。
- 可追问：DSL 如果有幻觉怎么办？→ `DslCompiler` 两道 Fail-Close 校验（结构合法 + 业务护栏：REPRICE≥成本、REALLOCATE≥0），不过编译就拒绝发布。
- 可追问：规则引擎执行会不会阻塞用户抢购？→ 走独立 0ms tryLock 的 `LocalLockService`（生产换 Redisson watch-dog），锁超时分级，不碰用户热段。

**Q9：Agent 的策略怎么「驱动」业务，而不只是做外围客服？**
- 要点：这是本项目区别于参考实现（MagTrade 等 agent 仅外围）的差异点——Agent 离线生成的策略 DSL，经编译后由规则引擎在线执行，而**规则引擎执行控盘指令时走与用户抢购相同的那把锁**（同一 `LocalLockService`），即「AI 的调度和用户抢购共享同一套强一致互斥」。不是另起炉灶，是复用热路径的锁。

**Q10：多智能体怎么协作？各自的角色？**
- Planner（拆 DAG）→ Data（取数校验）→ Viz（出图）→ Writer（成文）→ Critic（自检：数据支撑/图文匹配/幻觉）→ Orchestrator（总控/并发/回滚/traceId）。
- 离线规划链路：Planner → 选品/定价/预热/风控 Agent → GuardrailPolicyAgent 汇编 DSL → DslCompiler 校验 → 版本化发布。

## D. 监测与评估（项目亮点，体现工程成熟度）

**Q11：你用什么指标证明「Agent 真的有用、且安全」？**
- 双轨评估：① 客观硬指标优先（毛利率/售罄率/库存周转，`BigDecimal` 确定性算）；② 模板定性结论补充（非 LLM，零成本可单测不幻觉）。
- A/B：AI 控盘 vs 人工规则，双指标（售罄率 + 毛利率）**都不低于**人工才判 AI 胜（防「赔本冲量」假胜）。
- 正确失败率（红线）：Agent 该拒绝/该求助时主动拒绝（ASK/REFUSE/ESCALATE）的比例，**越高越安全**，且绝不把「正确拒绝」编造成功。

**Q12：怎么防止「改了新功能把老功能弄坏」？**
- golden 回归（历史正向 case 重跑，Phase 8 的 10 条）+ 失败样本回归重放（5 条危险输入，用 `forceInvalidPolicy=true` 编排器重放，断言仍被安全拒绝——证明护栏没退化）+ CI 门槛失败阻断（`EvaluationHarnessTest` 不通过构建就红）。

**Q13：评估闭环怎么接 CI？**
- `.github/workflows/eval.yml`：`mvn clean package` 即闸门；`EvaluationThresholds` 五道线（golden 100% / 回归 100% / AI 售罄率提升≥5% / AI 毛利≥20% / 正确失败率≤100%）。任一不过 → 测试失败 → 合并被拦截。
- 诚实：CI 在沙箱未实跑（无 runner），但门槛逻辑在 JUnit 层已被 `EvaluationHarnessTest` 可信验证（本地等价）。

## E. 工程与取舍（体现成熟度）

**Q14：为什么选 Drools 而不是自研规则引擎？**
- 要点：决策 #5 从初稿「自研」改为 Drools——纯 Java 库、零外部依赖、JDK21 沙箱可行；DSL→DRL 编译有成熟 Fail-Close 门禁；避免重复造轮子。

**Q15：模块间怎么解耦？为什么 rule-engine 对 agent-core 用 optional？**
- 要点：rule-engine 只需 agent-core 的 DSL 类型，用 `optional=true` 避免把 spring-ai/webflux 传染到 api 下游（曾因此踩过测试上下文加载坑）。大屏（api 侧）只读 agent/rule**已落库**的 trace/策略，零运行时耦合。

**Q16：项目里哪些是你觉得还不够、需要继续做的？**
- 诚实清单（加分项：主动说边界）：① 真 Redisson 集群 / Milvus / DeepSeek 接入（当前桩）；② 支付链路（当前延后）；③ Nginx 令牌桶 / Sentinel 纵深限流（部署增强）；④ 完整多租户 / 优惠券等（范围红线 M7+）。
- 态度：把「没做」当作「已规划 + 已知代价」，而不是回避。

## F. 一句话收尾（留给面试官的印象）

> 「这个项目我想证明一件事：AI Agent 不是用来给秒杀系统套个聊天壳，而是用**控制面/数据面分离**让它『离线聪明规划、在线确定性执行』，同时用评估闭环把『无超卖』和『AI 真有用』变成**可量化、可回归、CI 阻断**的硬指标——而且每一步我都诚实标注了哪些是真跑过的、哪些只是写好了配置。」
