# InsightForge（智析）本机实跑指南

> 配套文档：`README.md`（项目总览）、`tutorials/phase0~11.md`（手把手教程）、`面试讲解稿.md`。
> 本文目标：把仓库里「写就但未在沙箱实跑」的部分（前端大屏、Docker/Nginx/Grafana 部署、JMeter 百万压测、GitHub Actions CI）变成你本机**一步步能验证**的路径。
>
> ⚠️ **诚实边界重申**：以下命令在沙箱环境（无 Docker / 无 JMeter / 无浏览器）无法代你执行，全部由**你在本机**按本文操作验证。所有「预期输出」都来自已通过 `mvn` 验证的后端代码行为，不是凭空写的数字。

---

## 0. 先搞懂：为什么要分这么多运行方式

本项目后端在沙箱里已经用 `mvn clean package` 把 **83 个测试全跑绿**了（api 35 + agent-core 26 + rule-engine 22）。也就是说**代码逻辑是验证过的**。
但「代码逻辑对」和「整套系统在你机器上跑起来」之间还差一层——中间件（MySQL/Redis/Kafka）、前端、容器编排、压测工具，这些沙箱没有，需要你本机提供。

本文给你 **4 档递进的运行方式**，从「零依赖 30 秒看效果」到「生产级全栈压测」，按需取用：

| 档位 | 用途 | 需要装什么 | 对应诚实边界 |
|---|---|---|---|
| A. 本地零依赖冒烟 | 最快确认后端能起来 | 只需 JDK21 + Maven | 沙箱已等价验证（H2 内存库） |
| B. 真中间件全栈 | 跑真实 MySQL/Redis 链路 | + MySQL8 / Redis7（Kafka 可选） | 沙箱未实跑，本机可验证 |
| C. Docker 一键编排 | 生产拓扑（进程隔离 + Nginx + 监控） | + Docker Desktop | 沙箱未实跑，本机可验证 |
| D. JMeter 压测 + CI 闸门 | 定量证明无超卖 / eval 门槛阻断 | + JMeter / Git 推送触发 Actions | 沙箱未实跑，本机可验证 |

## 1. 前置准备（一次性）

```bash
# 1) JDK 21（项目用 JDK 21 语法，必须 21）
java -version            # 期望：openjdk version "21.x"

# 2) Maven 3.9.x
mvn -version             # 期望：Apache Maven 3.9.x

# 3) Git（拉代码 & 触发 CI）
git --version

# 4) 拉仓库
git clone <你的 Gitee 地址> insightforge
cd insightforge          # 仓库根 = D:/Java（或你 clone 的目录）

# 5) 可选：MySQL 8 / Redis 7（档位 B 需要）
#    macOS:  brew install mysql redis
#    Linux:  apt install mysql-server redis-server
#    Win:    用 Docker 起，或装 MySQL Installer + Redis for Windows（社区版）

# 6) 可选：Node 22（档位前端需要）
node -v                  # 期望：v22.x

# 7) 可选：JMeter 5.6.3（档位 D 需要）
#    官网下载解压，记下 JMETER_HOME
```

> 工具链提示：本项目在 JDK 21 下用 Maven Surefire 跑测试时，**若工程目录与系统临时目录跨盘符（如工程在 D:、temp 在 C:）**，Surefire 的 fork jar 会因 Manifest 绝对路径跨 root 被拒。父 POM 已加 `-Djdk.net.URLClassPath.disableClassPathURLCheck=true` 兜底；若你本机仍崩，跑测试前先 `export JAVA_TOOL_OPTIONS=-Djava.io.tmpdir=<与工程同盘的目录>`。同盘（如都在 C:）则无需任何处理。

## 2. 档位 A：本地零依赖冒烟（30 秒看后端起来）

不装任何中间件，用 H2 内存库 + 关闭 Redis/Kafka 自动配置，直接把 API 跑起来。

```bash
# 在仓库根目录
mvn -pl insightforge-api -am spring-boot:run -Dspring-boot.run.profiles=local
```

启动后另开一个终端验证：

```bash
curl http://localhost:8080/actuator/health
# 期望（关键字段）：
# {"status":"UP","components":{"db":{"status":"UP","details":{"database":"H2"}},"redis":{...可能 absent ...},"diskSpace":{"status":"UP"}}}

curl http://localhost:8080/actuator/prometheus | head
# 期望：能看到 insightforge_* 开头的业务 Gauge（大屏指标已注册）
```

**这一步等价于沙箱已验证的 `mvn clean package`**——区别只是沙箱用的是测试上下文，你这里跑的是真 Spring Boot 进程。能起来就证明脚手架 + 自动配置没问题。

> ❓ 想看大屏？档位 A 没有前端，跳到档位 B/C 之后再起前端（§5）。

## 3. 档位 B：真中间件全栈（跑真实 MySQL/Redis 链路）

### 3.1 起中间件

```bash
# MySQL（建库 + 授权，与 application.yml 默认配置一致）
mysql -uroot -p
CREATE DATABASE IF NOT EXISTS insightforge;
CREATE USER IF NOT EXISTS 'insightforge'@'localhost' IDENTIFIED BY 'insightforge';
GRANT ALL PRIVILEGES ON insightforge.* TO 'insightforge'@'localhost';
FLUSH PRIVILEGES;

# Redis
redis-server --daemonize yes
redis-cli ping            # 期望：PONG

# Kafka（可选，Phase 4 异步解耦才需要；纯秒杀热路径不强制）
# 用 Docker:  docker run -d -p 9092:9092 bitnami/kafka:3.7 ...（见 docker-compose kafka 段）
```

> 数据库表结构由 `src/main/resources/schema.sql` + 种子 `data.sql` 在启动时自动执行（`spring.sql.init.mode=always`），**不用手动建表**。

### 3.2 跑后端（用默认 profile，连 localhost 中间件）

```bash
mvn -pl insightforge-api -am spring-boot:run
# 注意：不指定 -Dspring-boot.run.profiles，默认走 application.yml（localhost:3306/6379/9092）
```

验证：

```bash
curl http://localhost:8080/actuator/health
# 期望 db 显示 MySQL、redis 显示 Redis UP

# 跑一次真实秒杀（默认种子 activityId=1, skuId=1）
curl -X POST "http://localhost:8080/api/seckill?activityId=1&skuId=1&userId=test001&qty=1"
# 期望：返回抢购结果 JSON（含订单号 / 剩余库存）

# 大屏数据 API（Phase 10 可观测）
curl http://localhost:8080/api/dashboard/overview
curl http://localhost:8080/api/dashboard/traces
curl http://localhost:8080/api/dashboard/guardrails
```

### 3.3 跑全套单元测试（验证 83 测试仍全绿）

```bash
mvn clean package
# 期望：BUILD SUCCESS，末尾各模块 Tests run: 35/26/22，0 failures
```

## 4. 档位 C：Docker Compose 一键编排（生产拓扑）

> 文件：`deploy/docker-compose.yml`（含 mysql/redis/kafka/api/agent-worker/rule-engine-worker/nginx/prometheus/grafana）。
> 设计要点（控制面/数据面分离在部署层 = 进程隔离）：`api` 是秒杀热路径接入层；`agent-worker` 离线生成 DSL（绝不进热路径）；`rule-engine-worker` 消费 `sales.tick` 在线执行。**每个 Worker 单独 limits**，避免 AI 规划挤占秒杀资源。

```bash
# 前置：装好 Docker Desktop 并启动
docker --version
docker compose version

# 在仓库根目录（compose 用 ../deploy/Dockerfile.* 构建，context 为 ./insightforge）
docker compose -f deploy/docker-compose.yml up -d --build
# 首次会拉镜像 + maven 多阶段编译，较慢（5~15 分钟）

docker compose ps
# 期望：所有服务 State 为 running/healthy
```

起来后访问：

| 组件 | 地址 | 说明 |
|---|---|---|
| 秒杀 / 大屏 API（经 Nginx） | http://localhost/api/... | Nginx 80 入口，秒杀路径带令牌桶限流 |
| 直连 API | http://localhost:8080 | 绕过 Nginx |
| 前端静态资源 | http://localhost | Nginx 反代 + 挂载 vite build 产物 |
| Prometheus | http://localhost:9090 | 抓 `insightforge_*` 指标 |
| Grafana | http://localhost:3000 | 默认 admin/admin，已 provision 数据源 + 看板 |

**Nginx 限流**：`deploy/nginx/nginx.conf` 对 `/api/seckill` 配了令牌桶（`limit_req zone=seckill_zone burst=20 nodelay`，每 IP 100 r/s），秒杀入口在大门口削峰。

**停止**：

```bash
docker compose -f deploy/docker-compose.yml down        # 保留数据卷
docker compose -f deploy/docker-compose.yml down -v     # 连数据卷一起清
```

## 5. 前端大屏（React + TS + Vite + Antd + ECharts）

> 目录：`insightforge-frontend/`，Phase 10 写就，沙箱无浏览器未实跑。本机按下面步骤即可起。

```bash
cd insightforge-frontend
npm install                 # 装依赖（首次较慢）
npm run dev                 # vite 启动，默认 http://localhost:5173
```

**关键：让前端能连上后端。** 检查 `insightforge-frontend/vite.config.ts` 是否配了 proxy：

```ts
// 期望有类似配置（把前端请求转给后端 8080）
server: {
  proxy: {
    '/api': 'http://localhost:8080',
    '/ws':  'ws://localhost:8080',   // 大屏 WebSocket 推送
  }
}
```

若没有，自行加上（或前端直连 `http://localhost:8080`）。配好后浏览器打开 http://localhost:5173：

- **Dashboard 页**：秒杀实时快照（售罄率/库存/在线护栏）+ WebSocket 推送刷新
- **TraceViewer 页**：Agent 决策链路 trace（trace_id 透传，离线规划可重放）
- **Hitl 页**：人工接管队列（Agent 该求助时 ESCALATE 的工单）

验证：`npm run build` 应 `tsc --noEmit && vite build` 通过（类型零错误）。产物在 `dist/`，可被 Nginx 挂载（档位 C）。

## 6. 档位 D-1：JMeter 百万抢购压测 + 无超卖对账

> 文件：`deploy/jmeter/seckill-load-test.jmx`（JMeter 5.6.3，2000 线程 × 50 loop，POST `/api/seckill`，userId=`${__threadNum}` 模拟不同用户）。

### 6.1 跑压测

```bash
# 先确保后端在跑（档位 B 或 C），且种子 activityId=1 有库存
# 打开 JMeter GUI 导入，或命令行无头跑：
$JETER_HOME/bin/jmeter -n \
  -t deploy/jmeter/seckill-load-test.jmx \
  -l deploy/jmeter/result.jtl \
  -e -o deploy/jmeter/report
# -n 无头 / -l 结果 / -e -o 生成 HTML 报告
```

**「百万级」怎么理解**：单机 100 万线程不现实。真实做法二选一——
1. **横向扩 slave**：JMeter 分布式（controller + 多 slave 把并发推到百万级）；
2. **放大 Loop**：单线程多请求（本计划 2000×50=10 万次请求，已能压出拐点）。

### 6.2 压测后无超卖对账（核心铁证）

压测结束，在 MySQL 客户端执行（与 Phase 2 `SeckillNoOversellTest`、Phase 6 `ReconcileService` 同一套逻辑）：

```sql
SELECT SUM(stock) AS remain, SUM(sold) AS sold, MIN(stock) AS min_stock
FROM activity_sku WHERE activity_id = 1;
```

**断言（两条必须同时成立）**：

```text
min_stock >= 0                              -- 绝不出现负库存（无超卖）
(初始库存 - sold) = remain                  -- 最终库存 = 初始 - 成功单数（exactly-once / 对账）
```

若 `min_stock < 0` 或两边不等 → 说明扣减有并发漏洞，**这就是 Phase 2 原子条件更新 + Lua 要守住的红线**，立刻回看 `tutorials/phase2.md` §5。

## 7. 档位 D-2：GitHub Actions CI 跑 eval 闸门

> 文件：`.github/workflows/eval.yml`。逻辑：`mvn -B clean package` 本身即闸门——`EvaluationHarnessTest` 断言 5 道评估门槛（golden 验收率 100% / 失败样本回归 100% / AI 售罄率提升≥5% / AI 毛利率≥20% / 正确失败率≤100%），**不通过则构建红、合并被阻断**。

### 7.1 触发

```bash
git add -A && git commit -m "..." && git push origin master
# 到 Gitee/GitHub Actions 页面看 eval.yml 是否绿
```

### 7.2 本机模拟 CI（不推送也能验）

```bash
# 等价于 CI 跑的闸门
mvn -B clean package

# 想看评估报告正文，再单独跑一次 gate CLI：
mvn -pl insightforge-agent-core exec:java \
  -Dexec.mainClass=com.insightforge.agent.core.evaluation.EvaluationGateMain
# 期望：打印 golden/回归/A-B/系统指标四段，结论 gatePassed=true
#        若任一门槛被打破，进程以 exit code 1 退出（与 CI 阻断行为一致）
```

**调门槛**：`EvaluationThresholds.defaults()` 在 `insightforge-agent-core/.../evaluation/EvaluationThresholds.java`。要改验收标准就改这里（如把售罄率提升门槛从 0.05 调到 0.10），CI 会自动跟着严。

## 9. 排错表

| 现象 | 可能原因 | 处理 |
|---|---|---|
| `mvn` 启动报 `ClassNotFoundException: plexus.classworlds...` | MinGW 把 MAVEN_HOME 解析成 Unix 路径 | 在 **cmd.exe** 里跑 `mvn`，或显式 `java -classpath "$MVN_HOME/boot/plexus-classworlds-2.8.0.jar" ... org.codehaus.plexus.classworlds.launcher.Launcher` |
| Surefire `The forked VM terminated without properly saying goodbye` | JDK21 跨盘符 fork jar 被拒 | 设 `JAVA_TOOL_OPTIONS=-Djava.io.tmpdir=<同盘目录>`；父 POM 已加 `disableClassPathURLCheck` 兜底 |
| 后端起不来，`com.mysql.cj.jdbc.exceptions.CommunicationsException` | 没起 MySQL 或密码不对 | 用档位 A（`-Dspring-boot.run.profiles=local`）零依赖先验证；或核对 `application.yml` 的 url/账号 |
| Redis `RedisConnectionFailureException` | 没起 Redis | 档位 A 已关闭 Redis 自动配置，先无 Redis 验证；档位 B 需 `redis-cli ping`=PONG |
| `/api/dashboard/*` 返回空或 404 | 大屏 API 依赖 persistence Mapper，需真实库 | 用档位 B/C 连 MySQL 再访问 |
| 前端白屏 / 接口 404 | vite proxy 没配或后端没起 | 检查 `vite.config.ts` 的 `/api`、`/ws` proxy；确认后端在 8080 |
| JMeter 报 `<url>... refused` | 后端没在 8080 / activityId 无库存 | 先 `curl` 通 `/api/seckill` 再压；调 jmx 里 `ThreadGroup.num_threads`/`loops` |
| CI 红但本机绿 | 门槛在 CI 环境数据不同 | 看 Actions 日志里 `EvaluationHarnessTest` 失败项，对照 §7.2 本机复现 |
| Docker `exec format error` | 非 x86 机器拉了 amd64 镜像 | 换对应架构镜像或加 `--platform` |
