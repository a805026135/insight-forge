# InsightForge（智析）分析文档 — 竞品 / 技术选型 / 重后端 / 大模型延迟红线

> 配套文档：`specs/insightforge/spec.md`（设计文档，已对齐至 v0.9）。
> 本文档回答四件事：① 竞品分析；② 每个技术选型的原因（为什么用 X 不用 Y）；③ 项目重后端，不贴切的 Agent 功能不硬加；④ 大模型延迟与一致性红线 —— LLM 不应进入秒杀热路径。
> 结论先抛：**本项目是后端高并发项目，Agent 是"离线/异步智能层"；LLM 永不进入秒杀热路径；Agent 通过"离线生成护栏策略 → 在线确定性规则引擎执行（写回同一份 Redis 库存键）"间接驱动热路径**——既保留差异化，又不踩延迟/一致性雷区。

---

## 0. 一句话定调

- **重后端**：权重约 70% 后端高并发工程（Redis+Lua 原子 / 分布式锁 / Kafka 削峰 / 限流 / 多级缓存 / 状态机 / JMeter 压测）+ 30% Agent 知识（规划 / 工具调用 / 记忆 / 反思 / 多 Agent 协作）。
- **Agent 不硬加**：只做 LLM 真正擅长且延迟可容忍的事（离线规划、异步复盘、离线生成护栏策略）；在线只跑确定性规则引擎 + 高并发引擎。凡是要把 LLM 塞进毫秒级热路径的，一律砍掉或改为规则执行。
- **延迟红线**：LLM 推理延迟（秒级，优化后数百 ms~50ms）、非确定性（同 prompt 不同输出）、知识截止、幻觉——四者与秒杀"毫秒级 + 强一致 + exactly-once"直接冲突，故 LLM 不进扣减/调价/再分配/下单热路径。

## 1. 竞品分析

### 1.1 市场全景（以 2026 年 618 大促为观察窗口）

2026 年 618 的明确叙事是"规则做减法，AI 做加法"——各平台把 AI 从辅助工具升级为经营基础设施。但**所有成功品的 AI 都落在投放 / 创意 / 客服 / 诊断 / 复盘等外围或辅助决策层，核心交易链路（扣减、锁、下单）仍是确定性系统**。

| 产品 | 定位 | AI 实际在干什么 | 是否碰库存扣减/锁（热路径） | 并发级别 | 与本项目关系 |
|---|---|---|---|---|---|
| **阿里妈妈 AI 万相**（万相台 AI 无界） | 全域 AI 投放中枢 | 四大 Agent（智识/智品/智造/智投）：消费者分层、预算调优、创意批量生成、全链路归因 | **否**，纯投放/创意层 | 投放侧高并发，非交易扣减 | 参照：AI 在经营外围，不碰锁 |
| **京东 京麦 AI 工具 + 京小智 + 稳赚计划** | 商家经营智能体 | 经营诊断、商品运营、营销投放、直播、客服、物流；"稳赚计划"承诺保投产比 | **否**，经营/投放层 | 中高（投放） | 参照：AI 参与经营决策但不进扣减 |
| **抖音 千川·乘方 / 快手磁力金牛 AI Agent** | 一站式智能营销 | 投放优化、AI 推广思维链展示、经营 Agent | **否** | 中高（投放） | 参照：营销层 AI |
| **豆包"帮你选" / 千问 AI 购物助手** | AI 购物入口 | 对话→推荐→比价→下单（用户侧） | 用户侧推荐，非商家侧锁 | 高（读多） | 参照：对话入口，不涉库存写 |
| **拼多多算法** | 定价/流量/推荐 | 算法渗透定价与流量分配 | 非 LLM Agent 叙事，规则/小模型 | 极高（但非 LLM 热路径） | 参照：核心用确定性算法 |
| **MagTrade**（前期调研） | 秒杀 + Agent | Agent 仅做外围客服 / 异常检测 | **否，不碰锁** | 高 | 缺口样本：Agent 未驱动热路径 |
| **抖粉智算**（前期调研） | 并发额度扣减 | 分布式锁 + 看门狗 + Lua 扣额度 | 是（工程范式，非 Agent 产品） | 高 | 范式来源：锁+Lua 的写法 |
| **运营多智能体 SaaS**（选品/定价/库存预警） | 经营多智能体 | 会改共享状态（库存预警/调价建议） | 中低并发，非秒杀级 | 中低 | 缺口样本：并发不够高 |

### 1.2 格局结论

1. **行业现状 = "外围场景火热、核心场景谨慎"**（支付领域工程文章的原文判断，同样适用于电商交易）。所有成功品都把 LLM 放在投放/创意/客服/诊断/复盘，核心链路用确定性规则引擎（Flink / Drools / 硬编码）。
2. **本项目的差异点不是"多加一个 Agent 功能"，而是把 Agent 产出的策略编译成在线护栏规则，与用户抢购争用同一份 Redis 库存键——在"核心场景"里让 AI 的智能以确定性方式落地。** 现有品没这么做：MagTrade 不碰锁，运营多智能体中低并发，平台级 AI 都在经营外围。
3. **但这个差异点必须尊重现实**：LLM 本身进不了热路径。所以我们落地的不是"LLM 现场决策"，而是"LLM 离线生成护栏策略 DSL → 确定性规则引擎在线执行"。这既保留了差异化，又满足"LLM 不进秒杀流程"的硬约束。

## 2. 技术选型原因（逐个 why X not Y）

| 选型 | 为什么用 X | 为什么不（或什么情况下不用）Y |
|---|---|---|
| **MySQL 8**（关系库） | ① 黑马点评/国内 Java 后端面试主流，资料与招聘生态最丰富，项目定位"面试项目+企业级"最稳；② 秒杀标准组合是 `Redis 预扣 + MySQL 行锁/乐观锁最终兜底`，大厂几乎都这么干；③ MyBatis-Plus 对 MySQL 支持最成熟；④ 读写分离、分库分表（ShardingSphere）、Canal 同步等中间件以 MySQL 为先；⑤ 容器化（docker-compose）一键起，国内云厂商支持最好 | **PostgreSQL**：JSONB/复杂查询/pgvector 强，但本项目结构化数据（商品/活动/订单/用户）用普通关系表即可；向量检索我们独立给 Milvus，PG"向量在库内"的优势用不上。PG 更"优雅"但偏离黑马点评范式与面试主流 → 不选。若未来想"向量+关系一体且规模小"，可降级为 PG+pgvector（见开放问题）。 |
| **Redis 7 + Redisson**（缓存/锁/限流） | ① 秒杀互斥心脏：库存扣减的共享可变状态真互斥；② Redisson 提供看门狗自动续期、可重入锁、公平锁、MultiLock、读写锁，解决裸锁的"过期释放/死锁/不可重入"三缺陷；③ 顺带做限流计数、订单去重、价格缓存 | 裸 `SETNX` 有三致命缺陷（无原子过期、硬编码过期、主从切换空窗重复获锁）→ 不用。Redis 单节点 CPU 上限靠库存分片 + 本地预热解决。 |
| **Redis + Lua 原子扣减** | `DECRBY` + 库存≥0 校验写在一段 Lua 里，避免"先 GET 再 DECR"的读-判-减竞态，保证不超卖 | 先查库存再扣减（应用层）在并发下必超卖 → 不用。Lua 把判断与写入变成单原子操作。 |
| **Kafka**（消息队列） | ① 异步削峰：下单峰值远超 DB 能力，先入队后异步建单；② 原生事件流：每次成交发销量事件，供护栏规则引擎在线控盘 + 异步复盘；③ 高吞吐、分区并行、至少一次语义 + 业务幂等 | **RabbitMQ**：更轻、易上手，但吞吐与"事件流"语义弱于 Kafka，且本项目要"销量事件流驱动控盘"，Kafka 的分区有序 + 重放更契合 → 选 Kafka。 |
| **Caffeine + Redis 多级缓存** | 进程内（Caffeine，μs 级）+ 分布式（Redis）两级，抗热点 key 失效、缓存击穿/雪崩；商品/活动配置高频读，本地缓存挡掉绝大多数 Redis 访问 | 单级 Redis：单点压力大、网络开销；单级本地：多实例不一致、重启丢失 → 两级互补。 |
| **Milvus**（向量库） | ① 企业级独立向量库，专为向量设计，千万~百亿级，独立扩展查询节点；② 多索引（HNSW/IVF/DiskANN/GPU CAGRA）、混合检索；③ 业界标准（10,000+ 企业团队，45K+ GitHub stars），展示"向量库独立扩展"能力；④ Agent 长期记忆（历史活动策略+结果）随活动积累增长，需独立扩展 | **pgvector**：≤5000 万向量、运维极简（PG 扩展）、事务一致，但违背"企业级独立扩展向量层"目标，且我们已用 MySQL 做关系库，不想再引入 PG → 不选。**Chroma**：偏原型/单机，生产感弱 → 不选。若规模长期 < 百万向量且想省运维，可降级 pgvector（见开放问题）。 |
| **Spring AI + DeepSeek** | ① Spring AI 标准化模型接入，自研 Agent Core 不绑死模型；② DeepSeek 中文/成本/推理均衡，适合规划期长文本推理 | 直接裸调厂商 SDK：耦合高、换模型成本高 → 用 Spring AI 抽象层。 |
| **Nginx + Lua 令牌桶** | 接入层限流，毫秒级、不占应用资源，挡掉绝大多数恶意/超限请求 | 只在应用层限流：粗粒度、保护晚 → 接入层先挡。 |
| **Sentinel** | 应用层限流/熔断/降级，按商品/用户/接口维度精细控制，保护后端 | 仅网关限流不够细 → Sentinel 补应用层。 |
| **确定性护栏规则引擎（Drools 9）** | 在线执行 Agent 离线生成的护栏策略（调价/再分配），写回同一份 Redis 库存键 `stock:a:{aid}:s:{skid}`（控制面在 Redisson 锁 `lock:a:{aid}:s:{skid}` 下串行化）；确定性强、μs~ms 级、可审计；超阈值转人工 | **LLM 在线决策**：延迟秒级、非确定、会幻觉 → 严禁进热路径（见 §4）。这正是"不硬加 Agent"的体现。 |
| **JMeter** | 百万级并发抢购脚本，构造初始库存 N，验证最终库存 = N − 成功单数、无重复订单，给出硬指标 | 仅靠单元测试无法证明高并发下不超卖 → 必须压测。 |
| **React + TS + Vite + Antd + ECharts** | 商户后台（建活动/看策略）+ 实时大屏；独立前端 + 后端 REST，职责清晰 | Vue 也行（见开放问题），默认 React 因生态/类型成熟度。 |
| **Docker Compose + GitHub Actions** | 一键起全部依赖（MySQL/Redis/Kafka/Milvus/API/Worker/前端）+ CI 跑 eval 回归 | — |

## 3. 重后端、不硬加 Agent

**原则**：Agent 只做"离线规划 + 异步复盘 + 离线生成护栏策略"；在线只跑确定性规则引擎 + 高并发引擎。

### 3.1 真贴合、保留的 Agent 功能（天然适合 LLM）
- **规划期选品 / 定价 / 预热 / 风控 Agent**：离线、长文本推理、可容忍秒级延迟——LLM 主场。
- **护栏策略生成 Agent（Guardrail Policy Agent）**：离线把活动目标编译成护栏 DSL（如"SKU-A 售罄速率 > 1.8× 预期且余量 < 阈值 → 自动从池 B 调拨 ≤ X 件；调价幅度上限 Y%；超出 → 人工"）。
- **复盘 Critic Agent**：活动结束后异步分析策略/控盘效果，写入 Milvus 形成数据飞轮。

### 3.2 不贴切、已弱化/不硬加的 Agent 功能
- **❌ LLM 实时控盘写锁（原 v0.5 设计）**：这是"为了炫 Agent 把 LLM 塞进热路径"的典型，已被砍。改为**确定性规则引擎在线执行**（LLM 只离线生成策略）。这正是用户"不贴切就不硬加"的体现。
- **⚠️ 智能客服 Agent**：外围、可选，不进核心链路；M5/M6 后期锦上添花。
- **⚠️ Viz / Writer Agent（出图/出方案文档）**：展示层增强，非核心，后期再做。
- **⚠️ 异常检测实时决策**：异常"检测"可异步（消费 Kafka 流做统计），但"处置动作"走规则引擎/人工，不靠 LLM 现场判断。

### 3.3 YAGNI（重申 spec §1.4）
不做完整多租户 SaaS 基建、不覆盖所有商品模型、不内置训练/微调、Agent 控盘不做完全无人值守自治（重大动作人工确认）。

## 4. 大模型延迟与一致性红线（关键论证）

### 4.1 事实：LLM 的四个本源缺陷（支付/银行/风控工程界共识）
1. **延迟高**：通用大模型推理秒级；即便深度优化（分层推理、蒸馏、prefix caching），端到端也只能压到数十~数百 ms。银行实时交易阻断场景的结论是"模型推理严格控制在 2ms，严禁大模型介入，只用剪枝后的轻量小模型（XGBoost）"。
2. **非确定性**：同 prompt 不同输出（Deterministic Inconsistency），与"强一致状态机"本质冲突。
3. **知识截止（Knowledge Cutoff）**：预训练后世界不再更新，无法感知秒级变化的实时库存/价格——**Agent 生成的内容在秒杀场景下天然可能是旧内容**。
4. **幻觉**：概率化输出，海量交易叠加下微小偏差会演变为巨额资金/库存错误。

### 4.2 秒杀热路径的硬约束
- 扣减 < 10ms、强一致（库存 ≥ 0 绝对准确）、exactly-once（无重复订单）。
- LLM 的上述四缺陷与这三条**直接冲突**：延迟会超时、非确定会超卖、旧内容会错配库存、幻觉会写错金额。

### 4.3 红线原则（写入 spec）
> **LLM 永不进入秒杀热路径（扣减 / 调价 / 再分配 / 下单）。** 在线只跑确定性规则引擎 + 高并发引擎。

### 4.4 落地：控制面 / 数据面分离（已被论文验证的架构）
2026 年一篇 LLM 驱动分布式事务的论文给出标准解法——**离线控制面用 LLM 作语义解析器生成 JSON DSL（策略），在线数据面用确定性代理执行**。这和我们完全一致：
- **控制面（LLM 离线）**：Guardrail Policy Agent 生成护栏策略 DSL + 复盘 Critic 写 Milvus。
- **数据面（确定性）**：护栏规则引擎读取 DSL，在 LIVE 期消费 Kafka 销量流，触发 `REPRICE`/`REALLOCATE`——**写回同一份 Redis 库存键 `stock:a:{aid}:s:{skid}`，控制面在 Redisson 锁 `lock:a:{aid}:s:{skid}`（0ms Fail-Fast）下 `INCRBY` 写回，与用户抢购争用同一份库存（用户 Lua 原子、AI 走锁，互不丢失更新）**。
- **结果**：Agent 通过"它生成的策略"间接驱动热路径（差异化保留），但 LLM 推理零热路径调用（红线遵守）。

### 4.5 缓存 / 预计算（空间换时间）
护栏策略与所需特征在规划期预计算入 Redis；在线只读 KV、算瞬时特征。呼应银行文章"智能体不能现场思考，要拿着预习好的答案做单选题"。

### 4.6 故障降级（fail-open）
规则引擎/锁任一环节超时 → 无缝降级到硬编码兜底规则，宁可牺牲部分精准度也绝不阻塞交易；LLM 不可用不影响秒杀主流程。

## 5. 对 spec v0.5 → v0.6 的修订点

v0.6 在 v0.5 基础上**只改与"LLM 不进热路径"冲突的部分**，其余（里程碑、结构、评估双维度）不变：
- **§1.1 定位句**："Live Control Agent 实时控盘走同一套锁" → "Guardrail Policy Agent 离线生成护栏策略 DSL，确定性规则引擎在线执行（走同一套锁）"。
- **§1.2 US-3**：改写为"规则引擎发现售罄过快 → 在护栏内自动再分配（走同一 Redisson 锁）；LLM 仅离线生成该护栏策略并异步复盘"。
- **§3.1 新增「大模型延迟红线」小节**：明确控制面/数据面分离，LLM 零热路径。
- **§3.3 全链路**：US-3 链路改为"离线生成 DSL → 在线规则引擎执行"。
- **§4 角色重映射**：`Live Control Agent` 拆为 `Guardrail Policy Agent`（离线生成 DSL）+ `Monitor/Alert Agent`（异步检测异常、超护栏转人工）。
- **§5.1 工具说明**：`repricer`/`reallocator` 标注为"由确定性规则引擎调用，非 LLM 直接调用；LLM 仅产出策略参数"。
- **§6.1 实时流**：由规则引擎消费，非 LLM。
- **M4/M6**：M4 加"护栏规则引擎"；M6 压测改为"百万抢购 + 规则引擎并发控盘（无 LLM 热路径）"。
