## 🌟 一句话记住整个项目的灵魂

> **AI 只在后台"写纸条"（想策略），现场抢购和调库存全靠"快又稳的程序"照纸条办，AI 本人绝不进抢购现场。**

这样 AI 能帮上忙，又不会因为 AI 慢/胡说把秒杀搞崩。

---

## 🔍 三个最核心的概念（重点看）

### 1. 护栏策略 DSL（你点名问的那个）
- **大白话**：一份**结构化的自动操作清单**，用固定格式写，程序直接读、直接执行，**不用大模型现场瞎想**。
- **拆开看**：
  - **DSL** = "领域特定语言" = 给程序读的"填空题格式"，不是文章，是填表。
  - **护栏策略** = "自动操作的边界规矩"，意思是 AI 可以自动干活，但**不能越过红线**。
- **生活类比**：你给超市夜班店员留的纸条——"可乐卖到只剩 5 箱，就从仓库调 10 箱上架；但要打折低于成本价，先打电话问我。" 这张纸条就是护栏策略 DSL：**规矩写死、店员（程序）照做、不用来回打电话问你（大模型）**。

### 2. 控制面 / 数据面分离
- **大白话**："动脑想规矩"和"现场真干活"分开。
- **控制面** = 动脑子想规矩的地方（大模型慢慢想、离线想）。
- **数据面** = 真刀真枪干活的现场（抢购、调库存，必须快、必须准）。
- **为什么分开**：大模型慢、还会胡说，所以只让它在"想规矩"时出场，干活现场不让它进。

### 3. 规则引擎
- **大白话**：一堆 `如果…就…` 的判断程序。**快、准、不胡来**，它不是大模型，就是照规则办事的机器。
- 在本项目：规则引擎读"护栏策略 DSL"这张纸条，发现条件满足就自动调价/调库存。

## 📚 术语速查表（按你会在哪一步遇到分组）

### 阶段一：搭环境和跑通主流程（Phase 0–1）
| 术语 | 大白话 |
|---|---|
| **Maven 多模块** | 把大项目拆成几个小盒子（引擎盒、Agent盒…），各管一摊，依赖统一管 |
| **Spring Boot** | Java 写网站/接口的主流框架，省去一堆配置 |
| **Docker Compose** | 一条命令拉起 MySQL/Redis/Kafka 等依赖，环境可复现 |
| **REST 接口** | 用网址（如 `/api/seckill`）让前端/工具调后端功能 |

### 阶段二：解决超卖和高并发（Phase 2–3，项目心脏）
| 术语 | 大白话 |
|---|---|
| **超卖** | 100 件库存卖出 105 单——绝对不能发生的事故 |
| **乐观锁 / 行锁条件更新** | 数据库里"扣库存时顺带检查还有没有货"，没货就不扣，第一道兜底 |
| **Redis** | 一个**超快的临时小仓库**（放库存数字），比正式数据库快百倍 |
| **Redisson 分布式锁** | 规则引擎控盘写（调拨/调价）时用来**排好队、一次只放一个改**，锁键 `lock:a:{aid}:s:{skid}` 与秒杀热路径同名；用户抢购热路径本身走 Redis Lua 原子（无显式锁，但原子不可打断） |
| **集成缝** | 把各模块的"桩环境自测"串成真实链路的接线：秒杀扣减后发 `sales.tick` → 规则引擎消费并读**同一份** Redis 库存、在**同一把锁**下写回——让「Agent 控盘与用户抢购争用同一库存」从原型变真实（本项目的 M7 核心工程） |
| **Lua 原子操作** | 把"看库存 + 扣库存"**打包成一步**，别人插不进来的操作，所以不会超卖 |
| **锁超时分级（0ms / 10ms）** | 用户抢购抢不到锁只等 10 毫秒就放弃说"请重试"；AI 调库存抢不到锁立刻放弃、待会儿重试——**保证用户永远优先** |
| **分段锁 / 只建新段** | 库存切成几段分别管；AI 调库存时**只新建一段**，不碰正在热卖的旧段，所以不拖慢用户 |

### 阶段三：削峰、缓存、限流（Phase 4–5）
| 术语 | 大白话 |
|---|---|
| **Kafka（削峰）** | 双十一洪峰先排进队列**慢慢处理**，别把系统冲垮 |
| **幂等（exactly-once）** | 同一个人手抖连点两次"抢购"，系统**只认一次**，不会下两单（订单号 = `OF-{活动}-{SKU}-{用户}`，不含数量 → 同一用户对同 SKU 限下一单，改量重试算重复单，这是有意规则） |
| **多级缓存（Caffeine+Redis）** | 热门数据放离 CPU 最近的地方，**少跑远路**加速 |
| **限流** | 人太多就**拦一部分**，保护系统 |
| **缓存击穿 / 雪崩 / 穿透** | 三种"缓存失效导致数据库被冲爆"的坑，各有对应解法（互斥锁重建 / 分片打散 / 布隆过滤器） |

### 阶段四：状态机与对账（Phase 6）
| 术语 | 大白话 |
|---|---|
| **状态机** | 活动/订单的"流程图"，规定只能 A→B→C，**不能乱跳**（如不能从"已结束"跳回"进行中"） |
| **对账** | 活动结束算一笔账：最终库存 = 初始 − 卖出数，验证**确实没超卖** |

### 阶段五：AI / Agent 部分（Phase 7–9）
| 术语 | 大白话 |
|---|---|
| **大模型 / LLM**（如 DeepSeek） | 会聊天的 AI，聪明但**慢、偶尔胡说** |
| **Agent（智能体）** | 给 AI 套个"能调用工具、自己排步骤"的壳，让它像员工一样干活 |
| **Agent Core（自研运行时）** | 我们自己写的"Agent 发动机"：管工具注册、记忆、反思，不依赖现成黑盒框架 |
| **三层记忆** | 短期（当前对话）、长期（Milvus 存历史方案）、跨 Agent（互相传纸条） |
| **Critic 反思** | 一个"审稿人"角色，发现策略不对（如价格低于成本）就打回重做 |
| **多智能体编排** | 好几个 Agent 分工（选品/定价/风控…），不是一个大 AI 一把梭 |
| **Guardrail Policy Agent** | 专门"写纸条"的 Agent——把活动目标变成护栏策略 DSL |
| **DSL 静态编译器（Fail-Close）** | 上线前先检查纸条写得对不对（格式/数字合法），**写错就禁止上线**，绝不运行时裸奔 |
| **两阶段预留（pending_stock）** | 调库存先"**占个坑**"，真用再确认；撤掉只取消占位，不影响已卖出的——防补偿时超卖 |
| **预测性调拨** | 不只等卖光才补，而是算"按这速度几分钟卖光"**提前补**，从救火变调度 |

### 阶段六：前端、监控、评估（Phase 10–11）
| 术语 | 大白话 |
|---|---|
| **可解释性** | 大屏上写清楚"**为什么**自动调了价"，让人看得懂 AI 在干啥 |
| **Prometheus / Grafana** | 监控工具：画曲线看"扣库存花多少毫秒、锁等了多久" |
| **JMeter 压测** | 模拟百万用户同时抢，验证系统扛不扛得住、超没超卖 |
| **双轨评估** | 用**硬数字**（毛利率、售罄率）为主 + AI 打分补充，证明项目真的有用 |
| **A/B 实验** | 一部分商家用 AI 控盘、一部分用老办法，对比谁效果好 |

### 通用基建词
| 术语 | 大白话 |
|---|---|
| **MySQL** | 正式数据库，存商品/订单/活动的"真相" |
| **Milvus（向量库）** | 把历史活动方案变成"**能按相似度搜**"的档案柜，下次类似活动参考 |
| **Nginx** | 网站的"大门"，做负载均衡和接入层限流 |
| **Sentinel** | 应用层"保险丝"，超时/过载就拦流量 |
| **CI（GitHub Actions）** | 每次提交自动跑测试和评估，不过关就卡住 |
